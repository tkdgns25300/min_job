# MinJob — 기획서

> 페이지·기능·역할 명세. 데이터 모델은 [`DATA.md`](./DATA.md), 아키텍처·컨벤션은 [`../CLAUDE.md`](../CLAUDE.md), 작업은 [`ROADMAP.md`](./ROADMAP.md).
>
> 구체 필드·enum 허용값은 여기 적지 않는다(축·개념만). 값은 DATA.md에서 확정한다.

## 개요

- **프로젝트명**: MinJob (민잡) — ministry + job
- **한 줄 설명**: 흩어진 교회 채용 공고(사역직 중심, 일반직 포함)를 모아 구조화·비교하게 해주는 채용 플랫폼
- **타겟 시장**: 한국 개신교(기독교) 교역자 청빙 전반 — 특정 교단에 한정하지 않는다
- **초기 집중 거점(beachhead)**: 예장합동·예장통합 (신학교 커뮤니티 접근성 + 개발자 인맥). **시장은 넓게, 초기 공고 확보·마케팅은 한 거점에 집중**
- **타겟 사용자**: 사역지를 구하는 교회 사역자(부목사·전도사 중심, 담임목사 포함), 청빙하는 교회
- **수익 모델**: 등록 무료 + 프리미엄 노출 유료 (교회 측 과금)

## 배경 (왜 이 제품인가 — 핵심만)

청빙 정보가 여러 신학교 게시판·교단 게시판·청빙넷 등에 흩어져 있어, 구직 교역자는 여러 사이트를 순회해야 한다. 기존 사이트들은 2000년대식 게시판이라 검색·필터·비교가 빈약하고, 공고가 자유 텍스트라 조건 비교가 안 된다. 청빙넷이 이미 "모아보기"를 표방하므로, MinJob의 차별점은 단순 수집이 아니라 **① 구조화(필터·정렬·비교) ② 교회 정보 연결(홈페이지·유튜브 링크)**이다. (③ 신뢰 정보 = 재공고 추적은 **보류** — 2026-08-07, DATA §6)

**스코프 — 개교회 채용(사역직 MINISTRY + 일반직 GENERAL, `jobs.job_kind`)을 다룬다. 주력은 사역직 부교역자(부목사·전도사)이며 목록 기본뷰도 사역직(`job_kind @> ARRAY['MINISTRY']` — 두 종류가 섞인 공고는 양쪽에 다 뜬다) — 일반직(방송·행정·시설·주방 등)은 필터로 노출한다(스코프 확장·운영자 확정 2026-07-28).** 담임목사 청빙은 노회 승인·공동의회 결의·청빙위원회 등 무거운 공식 절차가 얽혀 초기 물량은 적을 것으로 보이나, 실수요가 있어 **직분 옵션으로 포함**한다 (타겟 인터뷰 2026-07-02, [`INTERVIEWS.md`](./INTERVIEWS.md)).

> ⚠️ 사용자 니즈는 구직 전도사 1명(개발자 누나) 인터뷰 기반 **가설**이다. 운영하며 검증·갱신한다.

## 사용자 모델 (단일 계정 + 역할 view)

**계정은 하나.** 모든 계정은 기본 **사역자(MINISTER)** — 로그인만으로 검색·북마크·관심 교회 이용. **교회 인증**(증빙 서류 + 운영자 승인) 통과 시 같은 계정에 **교회(CHURCH) view**가 열려 자기 교회 공고를 관리한다. **"교회 전용 계정"은 없다**(교회는 엔티티, 사람 계정은 관리 자격). 데이터 모델 = DATA §3·§4.

| view/역할 | 누구 | 주요 행위 | 개방 조건 |
|---|---|---|---|
| **사역자(MINISTER)** | 모든 로그인 계정(기본) | 공고 검색·열람(비로그인도) · 북마크 · 관심 교회 · 새 공고 알림 | 로그인 |
| **교회(CHURCH)** | 인증된 교회 담당자 | 자기 교회 공고 등록·관리, 노출 결제 | 교회 인증 승인 |
| **운영자(admin)** | 본인(개발자) | 수집 공고 검수(`review_data`의 `PENDING`), 교회 인증 검수. ⚠️ ~~공고 전수 검수~~는 **철회**(2026-08-21 — 교회 인증이 등록 자격 게이트라 이중 게이트다) | allowlist |

- **가입 시 역할 선택 없음** — 로그인=사역자, 교회는 인증으로 승격(단일 정체성). 부교역자가 **구직 중이면서 자기 교회 공고 관리**도 가능(흔한 케이스).
- 구직자(사역자)는 **로그인 없이도 공고 열람**. 로그인 시 **북마크(Phase 1)** · 관심 교회·알림(Phase 2).
- **공고 소유 = 교회 엔티티**(가드레일 #2). 담당자는 관리 자격 — 편집 권한 = 그 교회 인증 관리자. 이동/다중 담당자는 DATA §3.
- 초기 공고는 운영자 manual seeding('운영자 등록', `source=OPERATOR`). 인증 교회가 **클레임**해 자기 교회 공고로 관리(운영자 등록 공고와 병존).

## 핵심 기능 — 접근 영역별

> 표준 채용 사이트(잡코리아·원티드·사람인) 공통 요소 중 **1인 운영 + "지원은 교회 연락처로 직접" 모델에 맞는 가벼운 것만** 채택. 이력서 DB·사이트 내 지원·포지션 제안 같은 무거운 양면 거래는 Phase 3로 미룬다.

### A. 공개 영역 (로그인 불필요) — 트래픽 핵심

- **홈 (`/`)**: 검색 + 스탯(모집 중·새 공고) + 추천 청빙(AD) + 최신 공고 — 상세는 아래 "페이지별 섹션(확정)"
- **공고 목록 (`/jobs`)**: 검색·필터(**사역직/일반직**·교단·지역·직분·부서·고용형태·사례비)·정렬. 기본뷰=사역직(`job_kind @> ARRAY['MINISTRY']`), 일반직은 필터. 구직자 메인 화면. **만료 공고는 목록에서 빠진다** — 마감일 경과 또는 상시모집 90일 초과(DATA §6-1). "지금 모집 중 N건"도 같은 기준
- **공고 상세 (`/jobs/[id]`)**: 구조화 정보 + 교회 홈페이지·유튜브 링크(★ 핵심 페인 해결) + 지원 안내(원문 보기 / 교회 홈페이지 — 사이트 내 지원 없음) + JobPosting JSON-LD
- **교회 상세 (`/churches/[id]`)**: 교회 정보(사진 갤러리·위치·채널) + 그 교회 공고·지난 공고 목록. 공고 상세에서 진입 — **교회 목록(browse)은 두지 않음**(구직자는 공고를 검색하지 교회를 훑지 않음; `/jobs` 교단·지역 필터가 대체, 리뷰·연봉 같은 enrichment도 없어 값 약함. 향후 필요 시 "교회 검색" 형태로만)
- **소개 (`/about`)**: 서비스 소개·신뢰 구축
- **공고 노출 안내 (`/pricing`)**: 노출 상품 안내(교회 대상). **top nav 아님** — footer + 교회 여정 맥락(공고 등록/관리·AD 섹션). (내용은 아래 "수익화" 섹션)
- **약관·개인정보처리방침 (`/terms`, `/privacy`)**: 로그인·개인정보를 다루므로 **필수**
- **문의**: 푸터 `mailto` (초기엔 폼 X — 스팸·운영 부담)

### B. 인증 영역 (로그인 필요) — 단일 계정, 인증으로 교회 view 개방

- **로그인 (`/login`)**: 간편 로그인 **구글 단독**(2026-07-29 실 전환 — 이메일/비밀번호 로그인 없음. **카카오·네이버는 오픈 범위 밖**, 2026-08-17 확정). **가입 시 역할 선택 없음**(로그인=사역자, 첫 로그인이 곧 가입). 전용 미니멀 레이아웃(박스 없음). 상세 = 아래 "로그인" 블록
- **교회 인증** (`/mypage`에서 진입): 교회 선택/생성 + 증빙 서류(고유번호증/사업자등록증) 업로드 → 운영자 승인. 승인 후 교회 view·공고 게재 활성. 미인증 상태로 공고 등록 시도 시 인증 유도
- **공고 등록·수정 (`/jobs/new`, `/jobs/[id]/edit`)**: **교회 인증 관리자만**(게이트). '교회 직접 등록'. 편집 권한 = 그 교회 인증 관리자. 등록 **무료**
- **마이페이지 (`/mypage`)** — 계정 상태별 (상세 = "마이페이지" 블록):
  - **사역자 view**(기본): 최근 본 공고 · **북마크(Phase 1)** · 관심 교회·새 공고 알림(Phase 2)
  - **교회 view**(인증 승인 시): 내 교회 공고 관리 + 요약 + 새 공고 등록 + 운영자 공고 클레임 + 교회정보. 헤더 view 토글
  - 미인증/검수중/반려 상태별 게이트 UI
- **(선택) 관심 조건 알림** (Phase 3): 표준 기능이나 알림 발송·운영 부담이 커 후순위

### C. 운영자 영역 (admin — 최소 형태로 유지)

거창한 시스템 ❌, **공고 입력·관리 작업대**로만. 공통 셸(`admin/layout` — 좌측 딥그린 사이드바[홈·수집 검수·공고·인증], 공개 헤더/푸터 없음, **noindex**(layout 상속)). **운영자 게이트**(2026-07-29): `.env` `ADMIN_EMAILS`(쉼표 구분) allowlist. `proxy.ts`가 `/admin/*`에서 비로그인은 307 `/login`, 로그인했어도 목록에 없으면 `/`로 보낸다(운영자 도구 존재 은닉). 판정은 JWT claims의 email로 해 추가 왕복이 없다. PII를 다루는 `/admin/verify`는 페이지에서도 `requireOperator()`로 재확인하고 아니면 `notFound()`. **목록이 비면 아무도 접근 못 한다(fail-closed).** 남은 것 = 실 DB 전환 시 operator RLS.

- **홈 (`/admin`)** — 요약 카드(노출중·이번주 등록·전체) + 빠른 작업 + 교회 인증 검수 링크 + **공개 목록 새로고침**(2026-08-22 · 캐시만 비우는 Server Action이라 화면이 바뀌지 않는다 → 버튼 옆에 "크롤러가 새 공고를 공개한 뒤. 안 눌러도 한 시간 안에 반영"을 적는다. 크롤러가 `jobs`에 직접 쓰기 때문에 필요한 장치다). `getAdminOverview()`(`'use cache'`), 서버 컴포넌트. "노출중" = OPEN 유료만. ⛔ **"검수 대기" 카드는 붙이지 않는다**(2026-08-22) — 건수는 캐시할 수 없는 미검수 데이터라(`lib/queries/review.ts`) 이 페이지가 `○ Static`을 잃는다. 대신 빠른 작업에 `/admin/review` 링크만 두고, 남은 건수는 그 화면 상단이 보여준다. 공고 전수 검수는 철회됐다(2026-08-21).
- **수집 검수 (`/admin/review`)** — 구현 완료(2026-08-22, 실 DB 직결). ⛔ **`/admin/ingest`를 대체했다**(결정 2026-08-21 · 코드 삭제 2026-08-22). 붙여넣기 도구와 `lib/ingest/structure.ts`(mock AI 휴리스틱)를 지웠다 — 수집원이 크롤러와 교회 직접 등록 둘뿐이 되면서 운영자가 직접 넣을 일이 없어졌다(가드레일 #1 개정).
  - **판정 규칙·enum 허용값의 정본은 `../min_job_agent/docs/SPEC.md`·`CONTRACT.md`** 다. `review_data`는 크롤러 소유 테이블이라 무슨 값이 무슨 뜻이고 무엇을 쓰면 안 되는지를 그쪽이 안다. 아래는 **그것을 화면으로 옮긴 것**이고, 어긋나면 그쪽이 이긴다.
  - **규모**: 전량 ~3,188건 중 자동 승인 77% · **이 화면에 오는 것 17%(~554건)** · 자동 거절 2%. ⚠️ **검수 554건의 96%가 "그림 때문"** 이다 → **이 화면의 성능은 "포스터를 얼마나 빨리 볼 수 있나"가 거의 전부를 정한다.**

  **화면은 셋이다. 나머지는 이 셋 안의 상태다.**

  | | 라우트 | 묻는 것 |
  |---|---|---|
  | ① 큐 목록 | `/admin/review` | 무엇을 봐야 하나 |
  | ② 단건 검수 | `/admin/review/[id]` | 이 값이 원문에 맞나 |
  | ③ 묶음 판정 | `/admin/review/[id]/group` | 이 둘이 같은 자리인가 |

  ⚠️ **③의 라우트는 `dedup_key`가 아니라 구성원 `id`다**(2026-08-22). 이유 둘: `dedup_key`엔 교회명(한글)이 들어가는데 라우트 id는 영어만 쓴다(CLAUDE.md 네이밍), 그리고 **판정 대상은 묶음이 아니라 그 안의 한 건**이라 id가 의미상 맞다(같은 묶음을 다른 구성원에서 열면 그 구성원이 대상이 된다).
  ⚠️ **③은 ②의 변형이 아니라 별개 화면**이다 — 묻는 것이 다르다. `dedup_state='UNCERTAIN'`인 행은 ②가 아니라 여기로 간다(한 건씩 보여주면 "옆 게시판 것과 같은 자리인가"를 판단할 수 없다).
  ⚠️ **②는 Sheet가 아니라 전체 화면 2단**이다. 청빙 포스터는 대개 **A4 세로**라 좁은 패널에 맞춰 축소하면 연락처·사례비 글자를 읽을 수 없고, 그 대조가 검수의 96%다.

  **① 큐 — 조건은 이것뿐이다**

  ```sql
  WHERE review_status = 'PENDING'
  ORDER BY created_at ASC          -- 오래 방치된 것 먼저
  ```

  ⚠️ **정렬 타이브레이크(`id`)는 `getQueueNavigation`과 짝이다**(2026-08-24). `created_at`이 같은 행이 생기면(크롤러가 한 트랜잭션으로 묶어 넣으면 Postgres `now()`가 고정돼 **전부 같아진다**) 목록과 앞뒤 이동의 정렬이 갈리고, 단건 화면의 "다음"이 목록의 다음 줄과 어긋난다. 묶음 화면의 줄 번호도 같은 이유로 `posted_on` 다음에 `id`로 못 박는다.
  ⚠️ **`confidence`로 필터하지 않는다** — 양쪽으로 어긋난다: 이단·마감으로 **이미 자동 거절된** 행이 딸려오고(거절이 등급보다 앞선다), 중복 판정이 `UNCERTAIN`으로 돌린 행은 **등급이 `high`인데 `PENDING`**이라 놓친다. 등급은 "왜 여기 왔나"를 보여주는 데만 쓴다.
  ⚠️ `posted_at`은 **중복 묶음의 최신 게시일로 덮이는 파생값**이라 정렬 기준이 못 된다.
  - 탭은 **검수 큐 / 처리한 것** 둘. 검색·확인 필요 유형·게시판 필터는 **큐 조건을 대체하지 않고 위에 얹는다**.
  - ⚠️ **확인 필요 유형 선택지는 고정 목록**(`ATTENTION_KINDS`)이다(2026-08-23). 화면에 있는 행에서 모으면 첫 100건에 없는 유형이 **선택지에 아예 나타나지 않아** 그 유형만 골라 보는 일이 불가능해진다. 게시판 선택지는 반대로 화면에서 모은다(31곳으로 늘 때마다 손대지 않기 위해).
  - ⚠️ **목록 타입에 원문을 담지 않는다**(2026-08-23). 목록 뷰가 client 컴포넌트라 `ReviewRow`에 든 것은 전부 **페이지 payload로 직렬화**된다 — 판정에 원문 길이·첨부 수가 필요해 DB에서 **읽기는** 하지만 세고 버린다(`ReviewSourceRef` = 게시판·게시일·수집일뿐). 원문 전부는 단건 전용(`ReviewSourceDetail`)이다.
  - **목록은 100건 상한**(2026-08-22). 한 행에 원문 텍스트와 배열 다섯 개가 달려 와, 첫 수집의 554건을 한 번에 내리면 payload가 MB 단위가 된다. 오래된 것부터라 **먼저 처리할 것이 먼저 온다**. ⚠️ 그래서 **탭 배지는 `length`가 아니라 전체 COUNT**를 쓰고(안 그러면 100에서 멈춰 거짓말한다), 잘렸으면 "전체 N건" 을 화면에 밝힌다.
  - 열: 교회명 · 지역 · 자리(`position[]` 또는 `role`) · 부서(69% 비어 있음 — 정상) · **확인할 것**(글) · 게시판 · 게시일
  - ⚠️ **게시판은 `키 · 한글 이름`으로 보여준다**(2026-08-23 · `boardLabel`). 키만으로는 어느 게시판인지 알 수 없고, 이름만 두면 운영자가 기억하는 키로 찾을 수 없다 — **키를 앞세우고 정렬도 키 순**이다(큐 행·원문 열은 이름만 쓴다: 그쪽은 읽는 자리다). 이름의 정본은 `../min_job_agent/config/sources.json`의 `board_name`(31곳)이고 `constants/review.ts`의 `SOURCE_BOARDS`가 **표시용 사본**이다(크롤러는 형제 리포라 런타임에 못 읽고, `source_data`에 이름 컬럼이 없다). 모르는 키는 **키를 그대로** 보여준다 — 새 게시판이 붙었을 때 화면이 비지 않고 "이름을 안 넣었다"가 보인다.
  - 인덱스는 크롤러가 이미 만들어 뒀다: `review_data_queue_idx (review_status, created_at)` · `review_data_dedup_key_idx (dedup_key)`

  **확인할 것 — 저장된 값에서 계산한다(등급 이유를 담는 칸은 없다)**

  **세 단계로 색이 갈린다**(`AttentionLevel` · 2026-08-23). 처음엔 색 없는 한 줄 글로 뒀는데 판정이 여러 개 붙는 행에서 **급한 것과 참고가 같은 회색**이라 구별이 안 됐다. 색은 장식이 아니라 **행동이 다르다는 표시**다 — 그래서 단계 이름이 곧 범례다:
  · **막힘**(`blocked`, 붉은색) 고쳐야 승인된다 — 지금은 `빈 칸`뿐이다 · **판단**(`judge`, 금색) 사람이 결론을 내야 한다 · **참고**(`note`, 회색) 알고만 있으면 된다.
  ⛔ 이모지는 쓰지 않는다. 알약형 배지도 아니다(작은 모서리 칩).

  `low` 승격 6칸 빔 → 빈 칸 · 게이트1 UNCERTAIN → 개교회 여부 애매 · 그림 못 받음 → 그림 못 받음 / `medium` **그림을 보냄 → 그림에서 읽은 값** · `contact_post`만 → 우편 접수만 · 이단 → 이단 목록 일치 / dedup UNCERTAIN → 같은 자리 불확실. 나머지(원문 없음·읽지 못한 첨부·교단 미확정·등급 low)는 우리가 더 얹은 것이다.
  → ⚠️ **한때 "그림에서 읽은 값"을 뺐다가 되돌렸다**(2026-08-23): "그림인 것은 문제가 아니라 정상 상태"라는 이유로 지웠더니 PENDING 69건 중 **8건(12%)이 "확인할 것 없음"** 으로 나왔다 — 전부 포스터 건이었고, 그것이 크롤러가 사람을 부른 **유일한 사유**였다. 흔한 사유는 **빼는 게 아니라 뒤로 미룬다**(급한 것이 앞에 오도록 판정 순서 마지막에 둔다).

  | **포스터 건(96%)** | **레코드 배너 하나** — "원문이 그림입니다. 값 전체를 포스터와 대조하세요." ⚠️ 필드별 "확인됨" 표시가 **거짓말이 된다** — 그림을 보낸 공고에서는 코드가 **어느 칸도 대조하지 않았다** |

  **구현(2026-08-22) — 배지가 아니라 칸 힌트로 넣었다.** 필드마다 색칠한 태그를 붙이지 않은 이유는 위 표의 논리 그대로다: 96%가 포스터 건이고 그 건에서는 **어느 칸도 대조되지 않아** 태그가 거짓말이 된다. 대신 힌트를 **칸을 펼칠 때** 낸다 — `설명`에 "AI가 쓴 요약", `연락처`에 "접수 주소는 원문 대조를 거치지 않은 조립 값", `지역`에 "항상 눈으로". 원문이 그림이면 "값 전체를 포스터와 대조" 안내를 원문 열에 상시로 둔다. 텍스트 건에만 붙는 필드별 태그는 만들지 않았다(태그 유무의 의미가 공고 종류에 따라 뒤집혀 오독을 부른다).

  **값은 읽기가 기본, 고치기는 펼쳐서**(2026-08-23) — 스무 칸을 전부 입력창으로 그려 놓으면 원문과 대조할 값이 컨트롤에 묶여 "결정할 게 너무 많은" 화면이 된다. 검수의 대부분은 **읽고 넘기는 일**이고 고치는 것은 몇 칸뿐이다.
  - 줄 하나 = `라벨 · 값 · [고치기]`. 펼치면 그 칸의 컨트롤과 힌트가 나온다. 접어도 **"고침"** 표시가 남아 손댄 줄을 알아볼 수 있다(`changedEdits` 결과를 그대로 쓴다).
  - 비어 있는 필수 칸은 값 자리에 **"비어 있음"**(강조)으로 — 승인이 막히는 이유가 고칠 자리에서 바로 보인다.
  - **구획은 공개 상세 화면과 같다**(2026-08-23 개정): 머리(교회명·제목·교단·지역·종류·직분·직무·부서·고용형태·사례비·마감일·게시일) → **모집 조건** → **자격 요건** → **우대 사항** → **공고 안내** → **전형 절차** → **위치** → **지원 방법**. ⛔ 검수용으로 따로 지은 이름(~~누가 뽑나~~·~~어떤 자리~~)은 **없앴다** — 검수는 "공개되면 이렇게 보인다"를 확인하는 일인데 화면이 공개 화면과 다른 말로 나누면 머릿속에서 한 번 더 옮겨야 한다. 구획 이름의 정본은 `(public)/jobs/[id]/job-detail-view.tsx`의 `<Section title>`이다.
  - ⚠️ **사례비 줄의 라벨은 값에 따라 바뀐다** — 사역직 `사례비` / 일반직 `급여`(`payLabel`이 정본 · DATA §3). 검수는 "공개되면 이렇게 보인다"를 확인하는 일이라 라벨도 공개 화면과 같아야 한다(2026-08-24 수정 — 큐에 일반직 5건이 `사례비`로 나가고 있었다). `ROW_LABELS`의 라벨 덮어쓰기는 **이 칸에만** 쓴다.
  - **확인 체크는 값 하나씩**이다(묶음 단위였던 것을 내렸다 · 2026-08-23). 키·라벨·개수의 단일 소스는 `value-rows.ts`이고 줄이 라벨을 거기서 읽으므로 **목록에 없는 줄은 만들 수 없다**(타입 에러) — 진행률의 분모가 화면과 어긋나지 않는다. ⚠️ **화면 상태일 뿐 저장하지 않고, 승인을 막지도 않는다** — 새로고침하면 사라지는 값으로 판정을 막으면 되돌리기 한 번에 일이 두 번 된다.
  - 탭 둘: **값 검수 / 공개 미리보기**. 미리보기는 공개 화면과 **같은 카드 컴포넌트**를 쓰고(검수용 사본을 만들면 공개 화면이 바뀔 때 조용히 거짓말을 한다) 값을 **공개 규칙대로 깎아서** 보여준다 — 교단은 근거가 확정이 아니면 빠지고, `pay_period`가 없으면 `jobs`의 DEFAULT대로 **월급으로** 나간다. 미상이라 **어느 필터에서 빠지는지**도 한 줄로 적는다(`/jobs`의 필터는 null을 탈락시킨다).
  - 판정 바(메모 + 저장만·거절·승인)는 **오른쪽 열 아래에 고정**한다 — 값이 길어 스크롤이 생기므로 버튼이 늘 손에 닿아야 한다. 막힌 이유는 **문장 하나**만 낸다(여러 줄을 쌓으면 읽지 않고, 그러면 이유를 모른 채 누른다).

  **열 너비는 원문 형태가 정한다**(2026-08-23) — 반반으로 고정하면 두 극단이 다 나쁘다: 포스터는 좁아서 확대해야 읽히고, 원문을 못 받은 건은 빈 상자가 화면 절반을 먹는다. 왼쪽 원문 열은 `sticky` — 값을 아래로 훑는 동안 포스터가 화면에서 나가면 대조가 끊긴다.

  | 원문 | 원문 : 값 |
  |---|---|
  | 그림(포스터 있음) | 58 : 42 |
  | 텍스트 | 46 : 54 |
  | 받지 못함 | 32 : 68 |

  - **포스터 뷰어**: 열 폭 맞춤 ↔ 2배 ↔ 3배 확대(가로 스크롤) · 새 탭으로 원본 · 여러 장 넘기기(`poster_paths` **배열 순서가 원문 순서**) · 장을 넘기면 배율은 초기화(확대된 채 넘어가면 어디를 보는지 모른다). **비공개 버킷이라 서버에서 signed URL**을 만든다. ⛔ **회전은 만들지 않았다**(2026-08-23) — 누워 있는 포스터가 실제로 있다는 측정이 없다.
  - ⚠️⚠️ **`poster_paths`에 이미지만 오지 않는다.** 크롤러는 **PDF도 같은 배열에** 담는다(실측 2026-08-23: jpg 75 · png 10 · **pdf 1**). `<img>`로 그리면 PDF가 **깨진 그림 아이콘**으로 나온다(운영자 발견 · PUTS 건). seam이 확장자로 `kind`(`image`/`pdf`/`other`)를 정하고 화면이 골라 그린다 — PDF는 브라우저 기본 보기 도구(`<iframe>`, 자체 확대를 갖는다), 모르는 형식은 **링크로 떨어진다**(확장자가 늘어도 다시 깨지지 않게). ⚠️ 크롤러는 **PDF·HWP를 Gemini에 보내지 않는다**(이미지만 · SPEC §6) — 그래서 PDF 포스터가 있는 건은 "읽지 못한 첨부"가 함께 뜨는 것이 맞고, 그 내용을 사람이 볼 수 있는 자리가 여기뿐이다.
  - **원문은 한 가지 모양으로만 보여준다**(2026-08-23). 한때 `우리가 받은 것 / 게시판 원문 그대로(iframe)` 토글을 뒀다가 **없앴다**: 본문(`raw_text`)이 이미 게시판 글 그대로라 96%는 프레임에서도 같은 것을 보고, 그 대가로 검수 한 건마다 보기 방식을 고르게 만들고 남의 게시판에 요청을 보냈다. 표·링크가 필요한 소수는 **게시판 원문 열기 ↗** 로 간다.
    → 실측 근거(PENDING 76건 · 2026-08-23): `raw_html`에 **표 2건 · 목록 1건**(4%)뿐이고 **49건은 `raw_html`이 비어 있다**(포스터 한 장인 게시판). 그래서 `raw_html`을 렌더하지도 않는다 — 남의 HTML을 `dangerouslySetInnerHTML`로 넣으려면 우리가 소독해야 하는데 그 위험을 4%와 바꾸지 않는다.
  - **본문은 문단으로 그린다** — `<pre>`로 두면 고정폭 글꼴에 원문의 빈 줄이 그대로 살아 **코드처럼 보이고 세로로 두 배** 길어진다. 청빙 공고는 읽어야 하는 글이다: 빈 줄을 문단 경계로 삼고(연속 빈 줄은 하나로), 문단 안 줄바꿈은 `whitespace-pre-line`으로 살린다. ⚠️ 안쪽에 스크롤을 두지 않는다 — 왼쪽 열이 이미 `sticky` + 스크롤이라 두 겹이 되면 바깥이 안 움직이는 구간이 생긴다.
  - 포스터가 안 뜨면(signed URL 서명 실패 등) **원문 링크를 크게** 띄운다 — "그림 못 받음"(경로가 애초에 없음)과 다른 상황이다.
  - 원문 텍스트가 **빈 문자열인 것은 정상**이다(본문이 이미지 한 장인 게시판) — 포스터가 있으면 "원문이 그림입니다", 그것마저 없으면 **"대조할 원문이 화면에 없습니다"**(승인하지 말라는 뜻)로 갈라 말한다.

  **첨부 레인**(2026-08-23) — 이름·개수를 보여주고 **원문 링크로 보낸다. 여기서 열지 않는다.**
  - 첨부 URL은 게시판 세션에 묶여 있어(그누보드 계열 4곳은 상세를 먼저 GET해야 파일이 온다 · 크롤러 SPEC §6) 우리 화면에서 링크를 걸면 `잘못된 접근입니다` HTML이 열린다.
  - **이름이 같은 것을 합쳐 "같은 이름 N줄"로** 보여준다 — 게시판이 같은 파일을 여러 줄로 낸다(실측: 지원서 하나가 9줄).
  - ⛔ **파일명으로 "공고문 / 지원 양식"을 가르지 않는다** — 크롤러 실측에서 289건 중 24건이 두 키워드에 **동시 매치**했다(`교역자 초빙 서류.hwp`). **확장자로 "구조화가 읽었을 수 있나"만** 가른다(이미지 = 읽음). 못 읽은 첨부가 있으면 "값의 근거가 이 문서 안에만 있을 수 있다"고 경고한다 — 본문이 "첨부파일을 참고 하시고 지원해 주세요," 한 줄인 공고가 실제로 있다(실측).

  **고칠 수 있는 칸** — 교회명 · 제목 · 종류 · 직분/직무명 · 부서 · 지역(광역+시군구) · 교단(+근거 자동) · 고용형태 · 사택(3-state + 원문 표현) · 사례비(최소~최대 + 주기 + 비정형) · 마감일 · 연락처 4칸 · 설명(2026-08-22) **+ 자격 · 주소 · 목록 칸 다섯**(`requirements`·`preferred`·`required_docs`·`optional_docs`·`process_steps` — 2026-08-23). 승격 6칸을 다 덮고, 거기에 **검색 축이 되는 칸**(지역·고용형태·자격), **노출 여부를 바꾸는 칸**(마감일), **지도가 쓰는 칸**(주소)을 더한 것이다. 마감일·게시일로 계산한 "승인해도 목록에 안 뜬다"는 경고를 판정 버튼 위에 띄운다(`isPubliclyOpen` 재사용).
  - **`requirements`를 열어 둔 이유**: `qualification`이 다섯 값뿐이어서 `본 교단 신학대학원`·`총회 인준 신학교` 같은 조건을 담을 수 없고, 그것이 빠지면 **다른 교단 지원자가 헛지원한다**(크롤러 실측 — 172건 중 23건에서 사라졌다). 나머지 넷도 지원자가 그대로 따라야 하는 것이라 성질이 같다.
  - 목록 칸은 **줄 단위로** 고치고·지우고·더한다. ⚠️ 한 덩어리 textarea로 두면 줄바꿈이 원소 구분이 되어 **원문에 줄바꿈이 있던 항목이 조용히 둘로 갈린다.** 빈 줄은 저장 전에 걷어낸다(`[""]`가 남으면 공개 화면에 빈 항목이 그려진다).
  - **여전히 못 고치는 칸**: 근무일 · 모집 인원 · 시작 시기 · 복리후생. 표시용이라 틀려도 지원 결과가 안 바뀌고, 칸이 늘면 한 건에 드는 시간이 늘어 큐가 밀린다 — 잘못됐으면 사유를 적고 거절한다. 화면은 **읽기 전용으로 보여준다**(승인은 "이대로 나가도 되나"를 묻는 일이라 나갈 것을 다 봐야 답할 수 있다).

  **쓰기 계약 — `review_data`만 쓴다**

  ```
  승인    고친 칸 + review_status='APPROVED' · reject_reason=NULL · reviewed_by · reviewed_at
  거절    review_status='REJECTED' · reject_reason='OPERATOR'(항상) · review_note(필수)
          · reviewed_by · reviewed_at        ← 고친 값은 저장하지 않는다(망가진 건도 거절해야 한다)
  되돌리기 ... WHERE id=$1 AND published_job_id IS NULL   ← 이 조건이 안전장치
  ```

  ⛔ **"저장만"은 없다**(2026-08-23 · 운영자 판단). 판정하는 두 길이 이미 `reviewed_by`를 찍으므로 "사람이 손댔다"는 표시에 빠지는 구멍이 없고, **값을 저장하는 경로는 승인뿐**이다. 오히려 저장만이 있으면 **판정하지 않은 행에 도장이 찍혀** 크롤러의 재구조화가 그 행을 건너뛴다 — 반쯤 고친 AI 초안이 영구히 굳는다. → `reviewed_by`가 찍힌 `PENDING` 행은 이제 **되돌린 건**뿐이고, 큐가 그렇게 표시한다.

  ⚠️⚠️ **중복 거절에 `reject_reason='DUPLICATE'`를 쓰지 않는다.** 크롤러는 그 값을 **자기가 내린 판정**으로 취급해 매 실행 처음부터 다시 보므로 **다음 실행이 거절을 풀어 버린다**(중복 규칙이 실측으로 계속 바뀌어 잘못 거절한 행이 되살아나야 하기 때문). 사람의 결론은 `'OPERATOR'`로 쓴다 — `OPERATOR`·`HERESY`·`CLOSED`는 결론 난 것으로 보고 판정에서 제외한다.
  ⚠️ **`reviewed_by`는 판정할 때 채운다.** 이 칸이 "사람이 손댔다"는 정본 표시고, 비면 **다음 재구조화가 사람의 교정을 AI 초안으로 되돌린다**(크롤러가 "지금 못 막는 유일한 구멍"이라고 적었다).
  → 그래서 **"오늘 처리"는 `reviewed_by`만으로 세지 않는다**(되돌린 건이 섞인다) — `review_status <> 'PENDING'`을 함께 본다. 큐 목록은 반대로 그 칸을 읽어 **"되돌린 건"** 을 표시한다.
  → **되돌리기는 사람이 내린 판정만** 대상이다. 크롤러 자동 판정(`reviewed_by` 빈 행)은 되돌릴 것이 없고(다음 실행이 다시 판단한다), 그래서 크롤러의 `DUPLICATE` 거절을 사람이 푸는 경로는 **만들지 않았다** — 풀려면 `dedup_state`(크롤러 계산값)도 함께 지워야 하는데 그건 다음 실행에 덮인다.
  → ⚠️ **되돌리기는 `reviewed_by`·`reviewed_at`을 지우지 않는다**(2026-08-22 수정). 지우면 "사람이 손댔다"는 표시가 사라져 **다음 재구조화가 운영자의 교정을 AI 초안으로 덮어쓴다** — 되돌리기는 "판정을 취소한다"는 뜻이고 "손댄 적 없다"가 아니다. 되돌린 행은 큐에서 "되돌린 건"으로 보인다.
  → ⚠️ **0행 UPDATE를 성공으로 읽지 않는다.** PostgREST는 조건에 맞는 행이 없어도 에러를 주지 않으므로 `.select("id")`로 바뀐 행을 돌려받아 확인한다. 안 하면 `published_job_id IS NULL` 안전장치가 막은 것을 화면이 "되돌렸습니다"라고 **거짓 보고**한다.
  - **손대지 않는 것**: `jobs`(크롤러가 공개한다) · `source_data`(write-once 원문 증거) · `dedup_key`·`dedup_state`·`confidence`·`published_job_id`·`posted_at`(전부 크롤러의 계산값. `dedup_state`는 중복 거절 해제 때만 예외)
  - **UPDATE는 한 번에 원자적으로** 보낸다 — 나눠 보내면 중간 상태가 CHECK에 걸린다.
  - ⚠️ **보내는 칸은 실제로 바뀐 것만**(2026-08-22). 안 고친 칸까지 함께 쓰면 운영자가 화면을 연 뒤 크롤러가 재구조화한 값을 **손댄 적 없는 칸까지 덮어쓴다**. 게이트는 고친 뒤의 **전체 상태**로, UPDATE는 **바뀐 칸만**으로 — `changedEdits`(lib/review-edits)가 그 둘을 갈라 준다. 짝(`job_kind`↔`position`·`role`, `denomination`↔`denomination_source`)은 화면 컨트롤이 언제나 함께 움직이므로 한쪽만 빠지지 않고, 그래도 어긋나면 CHECK가 막는다.

  **③ 묶음 — 같은 `dedup_key`를 나란히**
  - 제목은 **건수로** 묻는다("이 3건이 같은 자리인가?"). ⚠️ 자리 이름을 제목에 넣으면 직분이 `ETC`일 때 **"기타 — 같은 자리인가"** 가 되어 무슨 화면인지 알 수 없다(2026-08-23 수정). 자리·부서는 그 아래 설명 줄로 내린다.
  - 구성원 줄은 **제목이 첫 줄**이다. 접수 이메일을 앞세우면(이전 모양) 사람이 못 알아보는 문자열이 주인공이 되고 판단 재료가 안 보인다. `dedup_state`는 줄에 쓰지 않는다 — 전원이 `UNCERTAIN`이라 같은 말만 반복된다. 대신 **판정 대상 / 공개됨 / 거절됨 / 공개 대기 / 검수 대기**를 쓴다.
  - **갈리는 값을 건별로 적는다**(2026-08-23) — 칸 이름만 나열하면("다른 점 — 접수 이메일 · 사례비") 무엇이 어떻게 다른지 몰라 판단이 안 된다. `groupDifferences`가 `{label, values[]}`를 돌려주고 각 줄이 자기 값을 뽑아 라벨과 함께 보여준다. ⚠️ **제목은 비교 칸에 넣지 않는다** — 재게시는 제목을 조금씩 바꿔 올려 거의 항상 "다른 점"이 되고, 그러면 목록이 제목으로 찬다(제목은 첫 줄에 통째로 있다). ⚠️ 비교값은 **라벨로 바꿔서** 비교한다 — 이제 화면에 그대로 나가므로 `ASSOCIATE_PASTOR`가 보이면 안 된다.

  - ⚠️ **순서·표시 날짜는 `source_data.posted_on`이다 — `review_data.posted_at`이 아니다**(2026-08-22). 후자는 묶음의 최신 게시일로 **덮이는 파생값**이라 구성원끼리 같은 값이 되고, 그러면 "어느 것이 먼저 올라왔나"라는 이 화면의 핵심 근거가 사라진다. 같은 이유로 **큐 목록의 날짜 칸도 `posted_on`** 을 쓴다 — 파생 게시일은 단건의 "그대로 공개되는 값"에서 라벨과 함께 보여준다.
  - ⚠️ **묶음의 일부는 이미 공개돼 있다** — 크롤러가 대표는 내보내고 나머지만 검수로 돌린다. 구분은 `published_job_id IS NOT NULL`. **이미 공개된 구성원에는 쓰지 않는다.**
  - "크롤러가 고른 대표"는 표시할 수 없다 — 대표와 나머지에 똑같이 `UNCERTAIN`이 붙어 저장값으로는 구분이 안 된다. 대신 공개 여부와 `review_status`로 보여준다.

- **교회 인증 검수 (`/admin/verify`)** — 구현(mock, 2026-07-21): **유일한 검수 게이트**. 탭(검수중[기본]·인증 완료·반려·전체) · 필터(교단·지역·검색) · 테이블(교회[미검증이면 **미검증** 배지]·담당자·**사무용 연락처**·제출일·상태) · 행 [검토]/[상세] → **Sheet**(교회·담당자·증빙 확인 + 서류 열람 + 승인 / 반려[사유 입력]). 정렬 = 검수 대기 우선(오래된 신청 먼저). 컴포넌트 `admin-verify-view`·`verification-row`·`verification-sheet`, 목록 = `getVerifications()`. **dynamic**(운영자 전용 + 담당자 PII라 `'use cache'` 금지 — `<Suspense>` 안에서 `requireOperator()`가 쿠키를 읽어 dynamic, 운영자 아니면 `notFound()`; 실 승인/반려·알림은 Phase 1). 담당자 실명·직분·이메일은 검수 확인 목적 admin 전용 노출(공개 X, 가드레일 #3). **담당자 개인 전화는 아예 수집하지 않는다**(2026-08-18 — 사칭자가 자기 번호를 적고 자기가 받으므로 검증이 성립하지 않는다). 대조는 교회 **사무용** 연락처로 한다.
- → **거대 통계 대시보드·별도 교회관리 시스템은 안 만든다** (교회 생성·편집은 ingest/jobs 안에서 인라인).

## 수익화 — 광고·노출 (첫 매출 채널)

등록은 무료, **노출이 유료**. 교회가 결제하면 공고를 "더 많이·더 크게·눈에 띄는 위치"에 보여준다.

- **노출 등급**: 일반 / 프리미엄(목록 상단 고정 + 강조 배지) / 대표 광고(홈·목록 상단 추천 슬롯에 더 크게)
- **노출 위치·크기·기간 차등**: 요금에 따라 노출 위치·카드 크기·노출 기간을 다르게. 기간 만료 시 자동 강등
- **정렬 반영**: 프리미엄·대표 광고가 정렬에서 우선(정렬·필터 규칙 표 참조)
- 결제는 초기엔 수동 처리, 자동 결제 연동은 Phase 3

> **노출 상품은 2종(프리미엄·대표광고)으로 진행**한다. 끌어올리기(bump)·강조 add-on은 공고량이 적고 단순성이 니치의 무기라 **제외**(공고량 늘면 재검토). **가격은 앵커로 공개**(프리미엄 7만원/주·대표광고 15만원/주, 주 단위·4주 묶음 할인)하되 **결제만 "문의"** — 초기엔 무료·할인 시딩(정가는 내리긴 쉬워도 올리긴 어려움). 실단가·부가세·최종 확정은 Phase 2, 라이브 결제·구좌 예약 없음. *사용자 노출 라벨 = **"공고 노출 안내"**.* 배너 광고(기독 B2B)는 Phase 2+ 옵션. **수익 모델 5종·노출 레버 7종·조사 근거 상세 = SNAPSHOT §9.**

## 의도적으로 안 하는 것 (스코프 보호)

- **사이트 내 지원·이력서 DB·포지션 제안** → Phase 3. 무거운 양면 거래라 1인 운영 제약과 충돌. 초기엔 "지원은 교회 연락처로 직접".
- **교회 리뷰·평점** → 하지 않음. 좁은 기독교 공동체에서 명예훼손·분쟁 리스크가 큼. "신뢰 정보"는 **객관 데이터로만** 제공(재공고 추적은 현재 보류 — DATA §6).
- **거대 admin 대시보드·통계** → 안 함(1인 운영). 단 검수·인증 대기 카운트 + 바로가기 수준의 **미니 "할 일" 홈**(`/admin`)은 둔다.

> **미claim 공고(`church_id = NULL`)의 축소 표시 — 확정 2026-08-16 (DATA §3)**
> 교회 식별을 claim으로 미뤘으므로 **소속 교회를 모르는 공고가 정상적으로 존재**한다. 그 경우:
> - **9번 교회 정보 섹션을 통째로 생략**한다 — `churches` 행이 없어 창립연도·채널·상세가 전부 없다. 빈 껍데기를 그리거나 "아직 등록되지 않은 교회예요" 같은 **내부 데이터 사정을 설명하지 않는다**(구직자에게 의미 없는 정보다). "이 교회의 다른 모집"도 이 섹션 안이라 함께 사라진다.
> - **헤더의 교회명은 남긴다**(공고의 정체성) — 다만 걸 상세 페이지가 없으므로 **링크가 아닌 평문**.
> - **6번 위치**: **주소·지역·시가 전부 미상이면 섹션째 생략**. 교회명만으로 지도를 검색하면 동명 교회의 엉뚱한 위치를 짚는다. (교회 상세 `/churches/[id]`도 같은 규칙 — `lib/format.ts`의 `naverMapUrl`·`churchPlaceLine`이 단일 소스) ⚠️ 이 규칙만은 **미claim 전용이 아니다** — `churches`의 위치도 전부 NULL 가능이라 claim된 교회에도 발동한다.
> - **지원 방법(우측 카드)**: 미claim이어도 `jobs.contact_*`는 공고에서 뽑은 값이라 **그대로 뜬다**. 교회 홈페이지를 모르므로 보조 링크는 원문(`source_url`)이 맡는다.
>
> **교단·지역 미상 표기(공통)** — 공개 화면은 **그 조각을 생략**한다(구분점까지 함께 — `" · 1985년 설립"`처럼 점이 앞에 매달리면 안 된다). 방문자에게 "미상"은 정보가 아니라 잡음이다. **교단·지역을 표시하는 운영자 화면은 "미상"을 명시**한다 — 검수에서 채워야 할 값이기 때문(해당 화면은 `/admin/review`). 표기 규칙의 단일 소스는 `lib/format.ts`의 `denominationLabel`·`churchLocation`·`churchMetaLine`.
>
> **표시값의 출처 규칙** — `lib/job-church.ts`의 `jobChurchRef`가 단일 소스다: **`jobs`에 컬럼이 있으면 그 값이 표시 정본**(`church_name`·`region`), 없는 것만 `churches`에서 온다(교단·시). 지역으로 거르는 코드(`getSimilarJobs`의 "같은 지역", 앞으로의 서버측 필터·`jobs(region)` 인덱스)가 전부 `jobs.region`을 보기 때문이다 — 표시만 교회 기준으로 바꾸면 **카드에 "서울"이라 적힌 공고가 경기 공고의 "같은 지역" 추천에 들어간다**. `jobs.church_name`은 **공고가 말한 그대로**라 claim 뒤에도 `churches.name`과 다를 수 있는데, 그건 의도다 — 공고 화면은 공고가 말한 이름을, 교회 상세(`/churches/[id]`)는 인증된 이름을 보여준다. 상세 페이지는 seam이 `JobDetail.churchRef`로 파생해 내려주므로 **페이지·뷰가 직접 조합하지 않는다** — 교회 프로필 섹션 제목도 `churchRef.name`을 쓴다.
