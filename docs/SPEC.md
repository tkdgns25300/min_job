## 개요

- **프로젝트명**: MinJob (민잡) — ministry + job
- **한 줄 설명**: 흩어진 교회 채용 공고(사역직 중심, 일반직 포함)를 모아 구조화·비교하게 해주는 채용 플랫폼
- **타겟 시장**: 한국 개신교(기독교) 교역자 청빙 전반 — 특정 교단에 한정하지 않는다
- **초기 집중 거점(beachhead)**: 예장합동·예장통합 (신학교 커뮤니티 접근성 + 개발자 인맥). **시장은 넓게, 초기 공고 확보·마케팅은 한 거점에 집중**
- **타겟 사용자**: 사역지를 구하는 교회 사역자(부목사·전도사 중심, 담임목사 포함), 청빙하는 교회
- **수익 모델**: 등록 무료 + 프리미엄 노출 유료 (교회 측 과금)

## 배경 (왜 이 제품인가 — 핵심만)

청빙 정보가 여러 신학교 게시판·교단 게시판·청빙넷 등에 흩어져 있어, 구직 교역자는 여러 사이트를 순회해야 한다. 기존 사이트들은 2000년대식 게시판이라 검색·필터·비교가 빈약하고, 공고가 자유 텍스트라 조건 비교가 안 된다. 청빙넷이 이미 "모아보기"를 표방하므로, MinJob의 차별점은 단순 수집이 아니라 **① 구조화(필터·정렬·비교) ② 신뢰 정보(재공고 추적) ③ 교회 정보 연결(홈페이지·유튜브 링크)**이다.

**스코프 — 개교회 채용(사역직 MINISTRY + 일반직 GENERAL, `jobs.job_kind`)을 다룬다. 주력은 사역직 부교역자(부목사·전도사)이며 목록 기본뷰도 사역직 — 일반직(방송·행정·시설·주방 등)은 필터로만 노출한다(스코프 확장·운영자 확정 2026-07-28).** 담임목사 청빙은 노회 승인·공동의회 결의·청빙위원회 등 무거운 공식 절차가 얽혀 초기 물량은 적을 것으로 보이나, 실수요가 있어 **직분 옵션으로 포함**한다 (타겟 인터뷰 2026-07-02, [`INTERVIEWS.md`](./INTERVIEWS.md)).

> ⚠️ 사용자 니즈는 구직 전도사 1명(개발자 누나) 인터뷰 기반 **가설**이다. 운영하며 검증·갱신한다.

## 사용자 모델 (단일 계정 + 역할 view)

**계정은 하나.** 모든 계정은 기본 **사역자(MINISTER)** — 로그인만으로 검색·북마크·관심 교회 이용. **교회 인증**(증빙 서류 + 운영자 승인) 통과 시 같은 계정에 **교회(CHURCH) view**가 열려 자기 교회 공고를 관리한다. **"교회 전용 계정"은 없다**(교회는 엔티티, 사람 계정은 관리 자격). 데이터 모델 = DATA §3·§4.

| view/역할 | 누구 | 주요 행위 | 개방 조건 |
|---|---|---|---|
| **사역자(MINISTER)** | 모든 로그인 계정(기본) | 공고 검색·열람(비로그인도) · 북마크 · 관심 교회 · 재공고 알림 | 로그인 |
| **교회(CHURCH)** | 인증된 교회 담당자 | 자기 교회 공고 등록·관리, 노출 결제 | 교회 인증 승인 |
| **운영자(admin)** | 본인(개발자) | 수집 공고 구조화·등록, 교회 인증 검수(공고 검수 없음) | allowlist |

- **가입 시 역할 선택 없음** — 로그인=사역자, 교회는 인증으로 승격(단일 정체성). 부교역자가 **구직 중이면서 자기 교회 공고 관리**도 가능(흔한 케이스).
- 구직자(사역자)는 **로그인 없이도 공고 열람**. 로그인 시 **북마크(Phase 1)** · 관심 교회·알림(Phase 2).
- **공고 소유 = 교회 엔티티**(가드레일 #2). 담당자는 관리 자격 — 편집 권한 = 그 교회 인증 관리자. 이동/다중 담당자는 DATA §3.
- 초기 공고는 운영자 manual seeding('운영자 등록', owner 없음). 인증 교회가 **클레임**해 자기 교회 공고로 관리(운영자 등록 공고와 병존).

## 핵심 기능 — 접근 영역별

> 표준 채용 사이트(잡코리아·원티드·사람인) 공통 요소 중 **1인 운영 + "지원은 교회 연락처로 직접" 모델에 맞는 가벼운 것만** 채택. 이력서 DB·사이트 내 지원·포지션 제안 같은 무거운 양면 거래는 Phase 3로 미룬다.

### A. 공개 영역 (로그인 불필요) — 트래픽 핵심

- **홈 (`/`)**: 검색 + 스탯(모집 중·새 공고) + 추천 청빙(AD) + 최신 공고 — 상세는 아래 "페이지별 섹션(확정)"
- **공고 목록 (`/jobs`)**: 검색·필터(**사역직/일반직**·교단·지역·직분·부서·고용형태·사례비)·정렬. 기본뷰=사역직(MINISTRY), 일반직은 필터. 구직자 메인 화면
- **공고 상세 (`/jobs/[id]`)**: 구조화 정보 + 교회 홈페이지·유튜브 링크(★ 핵심 페인 해결) + 재공고 정보 + 지원 안내(원문 보기 / 교회 홈페이지 — 사이트 내 지원 없음) + JobPosting JSON-LD
- **교회 상세 (`/churches/[id]`)**: 교회 정보(사진 갤러리·위치·채널) + 그 교회 공고·재공고 이력(패턴 가시화). 공고 상세에서 진입 — **교회 목록(browse)은 두지 않음**(구직자는 공고를 검색하지 교회를 훑지 않음; `/jobs` 교단·지역 필터가 대체, 리뷰·연봉 같은 enrichment도 없어 값 약함. 향후 필요 시 "교회 검색" 형태로만)
- **소개 (`/about`)**: 서비스 소개·신뢰 구축
- **공고 노출 안내 (`/pricing`)**: 노출 상품 안내(교회 대상). **top nav 아님** — footer + 교회 여정 맥락(공고 등록/관리·AD 섹션). (내용은 아래 "수익화" 섹션)
- **약관·개인정보처리방침 (`/terms`, `/privacy`)**: 로그인·개인정보를 다루므로 **필수**
- **문의**: 푸터 `mailto` (초기엔 폼 X — 스팸·운영 부담)

### B. 인증 영역 (로그인 필요) — 단일 계정, 인증으로 교회 view 개방

- **로그인 (`/login`)**: 간편 로그인 **구글 단독**(2026-07-29 실 전환 — 이메일/비밀번호 로그인 없음, 카카오는 오픈 전 추가·네이버 보류). **가입 시 역할 선택 없음**(로그인=사역자, 첫 로그인이 곧 가입). 전용 미니멀 레이아웃(박스 없음). 상세 = 아래 "로그인" 블록
- **교회 인증** (`/mypage`에서 진입): 교회 선택/생성 + 증빙 서류(고유번호증/사업자등록증) 업로드 → 운영자 승인. 승인 후 교회 view·공고 게재 활성. 미인증 상태로 공고 등록 시도 시 인증 유도
- **공고 등록·수정 (`/jobs/new`, `/jobs/[id]/edit`)**: **교회 인증 관리자만**(게이트). '교회 직접 등록'. 편집 권한 = 그 교회 인증 관리자(owner 일치 아님). 등록 **무료**
- **마이페이지 (`/mypage`)** — 계정 상태별 (상세 = "마이페이지" 블록):
  - **사역자 view**(기본): 최근 본 공고 · **북마크(Phase 1)** · 관심 교회·재공고 알림(Phase 2)
  - **교회 view**(인증 승인 시): 내 교회 공고 관리 + 요약 + 새 공고 등록 + 운영자 공고 클레임 + 교회정보. 헤더 view 토글
  - 미인증/검수중/반려 상태별 게이트 UI
- **(선택) 관심 조건 알림** (Phase 3): 표준 기능이나 알림 발송·운영 부담이 커 후순위

### C. 운영자 영역 (admin — 최소 형태로 유지)

거창한 시스템 ❌, **공고 입력·관리 작업대**로만. 공통 셸(`admin/layout` — 좌측 딥그린 사이드바[홈·수집·공고·인증], 공개 헤더/푸터 없음, **noindex**(layout 상속)). **운영자 게이트**(2026-07-29): `.env` `ADMIN_EMAILS`(쉼표 구분) allowlist. `proxy.ts`가 `/admin/*`에서 비로그인은 307 `/login`, 로그인했어도 목록에 없으면 `/`로 보낸다(운영자 도구 존재 은닉). 판정은 JWT claims의 email로 해 추가 왕복이 없다. PII를 다루는 `/admin/verify`는 페이지에서도 `requireOperator()`로 재확인하고 아니면 `notFound()`. **목록이 비면 아무도 접근 못 한다(fail-closed).** 남은 것 = 실 DB 전환 시 operator RLS.

- **홈 (`/admin`)** — 구현(mock, 2026-07-21): 요약 카드(노출중·이번주 등록·전체) + 빠른 작업 + 교회 인증 검수 링크. `getAdminOverview()`(`'use cache'`), 서버 컴포넌트. "노출중" = OPEN 유료만. (공고 검수 제거로 "검수 대기"는 없음.)
- **공고 수집 (`/admin/ingest`)** — 구현(mock, 2026-07-21): 좌 **원문 붙여넣기**(사람이 확보) → **AI 구조화** → 우 **프리필 폼 검토·보정** → ‘운영자 등록’(소유자 없음, mock no-op). 교회는 **datalist 인라인 매칭**(기존 연결/신규 생성). 구조화 seam = `lib/ingest/structure.ts`(**mock 키워드 휴리스틱** — 교단·지역·직분[담임 최후순위]·부서[중점 라벨]·고용형태·사례비[금액 우선]·마감[키워드 앵커]·URL 추출). ★ **수집원 2종**: 크롤러(`min_job_agent`, 공개 공식 게시판 자동 수집) + 사람 붙여넣기 — 둘 다 수집원. 크롤러 산출은 리뷰 큐(`review_data`)로 들어와 **운영자 검수 후 승격**(자동 공개 없음, §C 검수 브릿지). ingest 화면 자체는 붙여넣기 경로. body는 요약(원문 통째 복제 X, 가드레일 #1 재정의: 공개 공식 게시판 한정 수집 허용·운영자 검수 전제·요약+출처 링크·개인정보 최소·opt-out·영리사이트 제외·법률검토 완료). 컴포넌트 `ingest-view`, 교회옵션 = `getChurchOptions()`(`'use cache'`, 공개). **Phase 1**: 구조화를 Server Action(Claude API, secret key)으로 이동(async 전환, 입출력 계약 유지) + 실 등록. ※ **초기 정형 데이터는 bulk import(seed)로 적재**, ingest는 **신규 원문 유입용**.
- **검수 브릿지 (리뷰 큐 → 게재)** — 명세(구현 = **크롤러 연동 트랙, ROADMAP 1-10**): `/admin/ingest`(붙여넣기)에 더해 **크롤러(`min_job_agent`)가 채운 `review_data`(PENDING) 검수 → 승인/수정 → `churches`/`jobs` 승격**. 승격 규칙 = **`source=OPERATOR` · `owner_id=NULL`(가드레일 #2) · 요약 body + `source_url`(원문 링크) + 지원용 공개 `contact`(가드레일 #3)**. 검수 처리: ① **미상 교단은 승격 전 해소**(enum 미승계 방지) ② **dedup은 병합 후보만 제시, 자동 병합 X**(운영자 판단) ③ **재공고는 병합하지 않는다**(재공고 이력 = MinJob 차별점, 별도 공고로 유지). 교회 매칭은 현 ingest datalist(기존 후보 제시 + 신규 생성) 재사용. + **크롤 대시보드** — `crawl_run`(최근 실행·신규 N·실패 M·시각) · `source_health`(게시판별 상태) · `review_data` **PENDING 카운트**. 크롤러 staging 4테이블 정의·소유 = `min_job_agent`(min_job은 직접 만들지·바꾸지 않음). 상세 = [`CRAWLER_HANDOFF.md`](./CRAWLER_HANDOFF.md).
- **공고 관리 (`/admin/jobs`)** — 구현(mock, 2026-07-21): 탭(전체·모집중·마감) · 필터(출처·교단·지역·검색) · 테이블(제목·교회·상태·노출등급·출처·게시일) · 행 액션(모집중=노출설정/수정 · 마감=재등록 + 케밥 마감/삭제) · **노출설정·수정 = Sheet**(mock, 실 저장 Phase 1). 케밥은 테이블 overflow 탈출 위해 body portal. 컴포넌트 `admin-jobs-view`·`admin-job-row`·`admin-job-sheet`·`admin-sidebar`, 목록 = `getAdminJobs()`. **공고 검수 없음**(교회 인증이 유일 게이트).
- **교회 인증 검수 (`/admin/verify`)** — 구현(mock, 2026-07-21): **유일한 검수 게이트**. 탭(검수중[기본]·인증 완료·반려·전체) · 필터(교단·지역·검색) · 테이블(교회[신규 배지]·담당자·증빙종류·제출일·상태) · 행 [검토]/[상세] → **Sheet**(교회·담당자·증빙 확인 + 서류 열람 + 승인 / 반려[사유 입력]). 정렬 = 검수 대기 우선(오래된 신청 먼저). 컴포넌트 `admin-verify-view`·`verification-row`·`verification-sheet`, 목록 = `getVerifications()`. **dynamic**(운영자 전용 + 담당자 PII라 `'use cache'` 금지 — `<Suspense>` 안에서 `requireOperator()`가 쿠키를 읽어 dynamic, 운영자 아니면 `notFound()`; 실 승인/반려·알림은 Phase 1). 담당자 연락처는 검수 확인 목적 admin 전용 노출(공개 X, 가드레일 #3).
- → **거대 통계 대시보드·별도 교회관리 시스템은 안 만든다** (교회 생성·편집은 ingest/jobs 안에서 인라인).

## 수익화 — 광고·노출 (첫 매출 채널)

등록은 무료, **노출이 유료**. 교회가 결제하면 공고를 "더 많이·더 크게·눈에 띄는 위치"에 보여준다.

- **노출 등급**: 일반 / 프리미엄(목록 상단 고정 + 강조 배지) / 대표 광고(홈·목록 상단 추천 슬롯에 더 크게)
- **노출 위치·크기·기간 차등**: 요금에 따라 노출 위치·카드 크기·노출 기간을 다르게. 기간 만료 시 자동 강등
- **정렬 반영**: 프리미엄·대표 광고가 정렬에서 우선(정렬·필터 규칙 표 참조)
- 결제는 초기엔 수동 처리, 자동 결제 연동은 Phase 3

> **노출 상품은 2종(프리미엄·대표광고)으로 진행**한다. 끌어올리기(bump)·강조 add-on은 공고량이 적고 단순성이 니치의 무기라 **제외**(공고량 늘면 재검토). **가격은 앵커로 공개**(프리미엄 7만원/주·대표광고 15만원/주, 주 단위·4주 묶음 할인)하되 **결제만 "문의"** — 초기엔 무료·할인 시딩(정가는 내리긴 쉬워도 올리긴 어려움). 실단가·부가세·최종 확정은 Phase 2, 라이브 결제·구좌 예약 없음. *사용자 노출 라벨 = **"공고 노출 안내"**.* 배너 광고(기독 B2B)는 Phase 2+ 옵션. **수익 모델 5종·노출 레버 7종·조사 근거 상세 = SNAPSHOT §9.**

## 의도적으로 안 하는 것 (스코프 보호)

- **사이트 내 지원·이력서 DB·포지션 제안** → Phase 3. 무거운 양면 거래라 1인 운영 제약과 충돌. 초기엔 "지원은 교회 연락처로 직접".
- **교회 리뷰·평점** → 하지 않음. 좁은 기독교 공동체에서 명예훼손·분쟁 리스크가 큼. "신뢰 정보"는 재공고 추적 같은 **객관 데이터로만** 제공.
- **거대 admin 대시보드·통계** → 안 함(1인 운영). 단 검수·인증 대기 카운트 + 바로가기 수준의 **미니 "할 일" 홈**(`/admin`)은 둔다.
