## 개요

- **프로젝트명**: MinJob (민잡) — ministry + job
- **한 줄 설명**: 흩어진 교회 채용 공고(사역직 중심, 일반직 포함)를 모아 구조화·비교하게 해주는 채용 플랫폼
- **타겟 시장**: 한국 개신교(기독교) 교역자 청빙 전반 — 특정 교단에 한정하지 않는다
- **초기 집중 거점(beachhead)**: 예장합동·예장통합 (신학교 커뮤니티 접근성 + 개발자 인맥). **시장은 넓게, 초기 공고 확보·마케팅은 한 거점에 집중**
- **타겟 사용자**: 사역지를 구하는 교회 사역자(부목사·전도사 중심, 담임목사 포함), 청빙하는 교회
- **수익 모델**: 등록 무료 + 노출 유료(사다리 3등급 · 교회 측 과금 — 수익화 절)

## 배경 (왜 이 제품인가 — 핵심만)

청빙 정보가 여러 신학교 게시판·교단 게시판·청빙넷 등에 흩어져 있어, 구직 교역자는 여러 사이트를 순회해야 한다. 기존 사이트들은 2000년대식 게시판이라 검색·필터·비교가 빈약하고, 공고가 자유 텍스트라 조건 비교가 안 된다. 청빙넷이 이미 "모아보기"를 표방하므로, MinJob의 차별점은 단순 수집이 아니라 **① 구조화(필터·정렬·비교) ② 교회 정보 연결(홈페이지·유튜브 링크)**이다. (③ 신뢰 정보 = 재공고 추적은 **보류** — 2026-08-07, DATA §6)

**스코프 — 개교회 채용(사역직 MINISTRY + 일반직 GENERAL, `jobs.job_kind`)을 다룬다. 주력은 사역직 부교역자(부목사·전도사)이며 목록 기본뷰도 사역직(`job_kind @> ARRAY['MINISTRY']` — 두 종류가 섞인 공고는 양쪽에 다 뜬다) — 일반직(방송·행정·시설·주방 등)은 필터로 노출한다(스코프 확장·운영자 확정 2026-07-28).** 담임목사 청빙은 노회 승인·공동의회 결의·청빙위원회 등 무거운 공식 절차가 얽혀 초기 물량은 적을 것으로 보이나, 실수요가 있어 **직분 옵션으로 포함**한다 (타겟 인터뷰 2026-07-02, [`INTERVIEWS.md`](./INTERVIEWS.md)).

> ⚠️ 사용자 니즈는 구직 전도사 1명(개발자 누나) 인터뷰 기반 **가설**이다. 운영하며 검증·갱신한다.

## 사용자 모델 (단일 계정 + 역할 view)

**계정은 하나.** 모든 계정은 기본 **사역자(MINISTER)** — 로그인만으로 검색·북마크·관심 교회 이용. **교회 인증**(증빙 서류 + 운영자 승인) 통과 시 같은 계정에 **교회(CHURCH) view**가 열려 자기 교회 공고를 관리한다. **"교회 전용 계정"은 없다**(교회는 엔티티, 사람 계정은 관리 자격). 데이터 모델 = DATA §3·§4.

| view/역할 | 누구 | 주요 행위 | 개방 조건 |
|---|---|---|---|
| **사역자(MINISTER)** | 모든 로그인 계정(기본) | 공고 검색·열람(비로그인도) · 북마크 · 관심 교회 · 새 공고 알림 | 로그인 |
| **교회(CHURCH)** | 인증된 교회 담당자 | 자기 교회 공고 등록·관리, 노출 결제 | 교회 인증 승인 |
| **운영자(admin)** | 본인(개발자) | 수집 공고 검수(`review_data`의 `PENDING`), 교회 인증 검수. ⚠️ ~~공고 전수 검수~~는 **철회**(2026-08-21 — 교회 인증이 등록 자격 게이트라 이중 게이트다) | allowlist |

- **가입 시 역할 선택 없음** — 로그인=사역자, 교회는 인증으로 승격(단일 정체성). 부교역자가 **구직 중이면서 자기 교회 공고 관리**도 가능(흔한 케이스).
- 구직자(사역자)는 **로그인 없이도 공고 열람**. 로그인 시 **북마크**(✅ 2026-08-28 계정 귀속 — 비로그인이 저장을 누르면 로그인으로) · 관심 교회·알림(Phase 2).
- **공고 소유 = 교회 엔티티**(가드레일 #2). 담당자는 관리 자격 — 편집 권한 = 그 교회 인증 관리자. 이동/다중 담당자는 DATA §3.
- 초기 공고는 운영자 manual seeding('운영자 등록', `source=OPERATOR`). 인증 교회가 **클레임**해 자기 교회 공고로 관리(운영자 등록 공고와 병존).

## 핵심 기능 — 접근 영역별

> 표준 채용 사이트(잡코리아·원티드·사람인) 공통 요소 중 **1인 운영 + "지원은 교회 연락처로 직접" 모델에 맞는 가벼운 것만** 채택. 이력서 DB·사이트 내 지원·포지션 제안 같은 무거운 양면 거래는 Phase 3로 미룬다.

### A. 공개 영역 (로그인 불필요) — 트래픽 핵심

- **홈 (`/`)**: 검색 + 스탯(모집 중·새 공고) + 추천 청빙(AD) + 최신 공고 — 상세는 아래 "페이지별 섹션(확정)"
- **공고 목록 (`/jobs`)**: 검색·필터(**사역직/일반직**·교단·지역·직분·부서·고용형태·사례비)·정렬. 기본뷰=사역직(`job_kind @> ARRAY['MINISTRY']`), 일반직은 필터. 구직자 메인 화면. **만료 공고는 목록에서 빠진다** — 마감일 경과 또는 상시모집 90일 초과(DATA §6-1). "지금 모집 중 N건"도 같은 기준
- **공고 상세 (`/jobs/[id]`)**: 구조화 정보 + 교회 홈페이지·유튜브 링크(★ 핵심 페인 해결) + 지원 안내(원문 보기 / 교회 홈페이지 — 사이트 내 지원 없음) + JobPosting JSON-LD
- **교회 상세 (`/churches/[id]`)**: 교회 정보(위치·채널 — 사진은 Phase 2) + 그 교회 공고·지난 공고 목록. 공고 상세에서 진입 — **교회 목록(browse)은 두지 않음**(구직자는 공고를 검색하지 교회를 훑지 않음; `/jobs` 교단·지역 필터가 대체, 리뷰·연봉 같은 enrichment도 없어 값 약함. 향후 필요 시 "교회 검색" 형태로만)
- **소개 (`/about`)**: 서비스 소개·신뢰 구축
- **공고 노출 안내 (`/pricing`)**: 노출 상품 안내(교회 대상). **top nav 아님** — footer + 교회 여정 맥락(공고 등록/관리·AD 섹션). (내용은 아래 "수익화" 섹션)
- **약관·개인정보처리방침 (`/terms`, `/privacy`)**: 로그인·개인정보를 다루므로 **필수**
- **문의**: 푸터 `mailto` (초기엔 폼 X — 스팸·운영 부담)

### B. 인증 영역 (로그인 필요) — 단일 계정, 인증으로 교회 view 개방

- **로그인 (`/login`)**: 간편 로그인 **구글 단독**(2026-07-29 실 전환 — 이메일/비밀번호 로그인 없음. **카카오·네이버는 오픈 범위 밖**, 2026-08-17 확정). **가입 시 역할 선택 없음**(로그인=사역자, 첫 로그인이 곧 가입). 전용 미니멀 레이아웃(박스 없음). 상세 = 아래 "로그인" 블록
- **교회 인증** (`/mypage`에서 진입): 교회 선택/생성 + 증빙 서류(고유번호증/사업자등록증) 업로드 → 운영자 승인. 승인 후 교회 view·공고 게재 활성. 미인증 상태로 공고 등록 시도 시 인증 유도
- **공고 등록·수정 (`/jobs/new`, `/jobs/[id]/edit`)**: **교회 인증 관리자만**(게이트). '교회 직접 등록'. 편집 권한 = 그 교회 인증 관리자. 등록 **무료**. **등록 전 클레임 패널**(2026-09-01) — 크롤로 이미 올라온 이 교회 공고가 있으면 위저드 전에 후보를 보여주고 [내 공고로 가져오기]/[해당 없음 — 새로 등록]. 가져오면 `church_id` 연결 + `source=CHURCH`(원문 링크·게시일 보존) 후 수정 화면으로 — **같은 자리 중복이 태어나는 유일한 지점을 등록 입구에서 막는다**. 후보 규칙 정본 = `lib/job-church.ts`의 `claimMatchTier`(이름 정규화 일치/포함 + 지역·교단이 둘 다 명시인데 다르면 제외 · 확정은 교회가) · 노출은 이 한 곳뿐(대시보드 상시 노출 안 함 — 운영자 2026-09-01) · 서버 액션이 규칙을 재판정하고 `church_id IS NULL` 재확인으로 동시 클레임 경합을 막는다. 후보는 **확실한 순으로 5개만 먼저** 보이고 [후보 N개 더 보기]로 펼친다 — 전부 펼치면 "해당 없음"(위저드로 가는 길)이 화면 밖으로 밀린다(12건 실측 1,086px). 실패 문구는 **그 줄 아래**에 남긴다(목록이 길면 어느 공고 이야기인지 알 수 없다). 후보 줄은 **공고에 적힌 교회명이 인증된 이름과 다를 때 그 이름을 앞세운다** — 느슨한 매칭(포함 관계)에서 남의 교회 공고를 가려낼 유일한 단서다. ⚠️ **수정 화면의 교회 카드·미리보기는 그 공고가 들고 있는 값**을 그린다(등록은 인증 교회 값) — 클레임 공고는 원문의 교회명·원문 링크를 유지하므로 인증 이름으로 그리면 공개 화면과 다른 말이 된다(문구도 "공개 화면에 이렇게 나가요."로 바뀐다)
- **마이페이지 (`/mypage`)** — 계정 상태별 (상세 = "마이페이지" 블록):
  - **사역자 view**(기본): 최근 본 공고 · **북마크**(✅ DB) · 관심 교회·새 공고 알림(Phase 2)
  - **교회 view**(인증 승인 시): 내 교회 공고 관리 + 요약 + 새 공고 등록 + 교회정보. 클레임(가져오기)의 입구는 대시보드가 아니라 **공고 등록 화면**이다(2026-09-01). 헤더 view 토글
  - 미인증/검수중/반려 상태별 게이트 UI
- **(선택) 관심 조건 알림** (Phase 3): 표준 기능이나 알림 발송·운영 부담이 커 후순위

### C. 운영자 영역 (admin — 최소 형태로 유지)

거창한 시스템 ❌, **공고 입력·관리 작업대**로만. 공통 셸(`admin/layout` — 좌측 딥그린 사이드바[홈·수집 검수·공고·인증], 공개 헤더/푸터 없음, **noindex**(layout 상속)). **운영자 게이트**(2026-07-29): `.env` `ADMIN_EMAILS`(쉼표 구분) allowlist. `proxy.ts`가 `/admin/*`에서 비로그인은 307 `/login`, 로그인했어도 목록에 없으면 `/`로 보낸다(운영자 도구 존재 은닉). 판정은 JWT claims의 email로 해 추가 왕복이 없다. PII를 다루는 `/admin/verify`는 페이지에서도 `requireOperator()`로 재확인하고 아니면 `notFound()`. **목록이 비면 아무도 접근 못 한다(fail-closed).** 남은 것 = 실 DB 전환 시 operator RLS.

- **홈 (`/admin`)** — **재설계 2026-08-25.** 이 화면이 답하는 질문은 하나다: **"지금 손댈 게 있나."** 하루 한두 번 열어 대부분은 "이상 없음"만 확인하고 닫으므로, **평상시엔 색이 하나도 없고** 이상이 있을 때만 눈에 띈다. 카드 셋, 주제 하나씩 — **들어오는 것 · 내가 손댈 것 · 나가는 것**.
  - **처리할 일** — 수집 검수 · 교회 인증. 각 카드는 대기 건수와 **가장 오래된 건**(적체 신호: 건수가 적어도 오래 묵었으면 손대야 한다)을 보여주고 그 화면으로 간다. 0은 숫자가 아니라 **"없음"**으로 쓴다 — `0`은 "세어 보니 0"인지 "아직 안 세었다"인지 읽는 사람이 모른다. 실측 정상 유입은 하루 35건 중 **검수 3건**이라(2026-08-24) 숫자 크기를 그 규모에 맞췄다.
  - **수집** — 마지막 실행 시각(`오늘 06:02`·`어제 18:04`·`3일 전 17:01`) + 새로 수집한 원문 수 + 게시판 성공/실패 + **실패한 게시판 이름**. **`CRAWL_OVERDUE_HOURS`(크롤 주기 한 번 = 24시간)를 넘기면 금색**이고 기록이 아예 없어도 같다. 처음엔 달력 날짜로 갈랐는데("오늘 돌렸나") 수집이 저녁에 도는 동안 **하루 18~20시간이 금색**이라 색이 뜻을 잃었다(운영자 지적 2026-08-25). **여유를 두지 않은 것은 선택이다**(운영자 확정 2026-08-25) — 손으로 돌리는 지금은 어제보다 늦게 돌린 날에 그 차이만큼 금색이 되지만, 여유를 한 주기 주면 크롤러가 죽어도 이틀 뒤에야 표시된다. **거른 날을 그날 안에 아는 쪽**을 골랐고, **매일 07:00 cron**(min_job_agent ROADMAP 1-7)이 올라오면 흔들림 자체가 사라진다. 이 판단이 크롤러 경보와 겹치지 않는 근거 — **크롤러는 자기가 안 돌았다는 사실을 스스로 기록할 수 없다**(프로세스가 안 뜨면 아무것도 쓰지 않는다). 실패한 게시판 **이름**도 판정이 아니라 사실이라 보여준다(`crawl_run.error_detail`의 키 · `boardLabel`) — 이름은 **게시판 목록으로 가는 링크**(`boardUrl` · 크롤러 `config/sources.json`의 `list_url` 사본 · 2026-08-29)이고, 크롤러가 남긴 에러 문구는 링크의 `title`로만 붙인다(길고 기술적이라 본문에 그리지 않는다) — 개수만 말하면 어디가 깨졌는지 알려고 터미널을 여는 수밖에 없어 그 줄이 있으나 없으나 같아진다. 원문 에러 문구는 넣지 않는다(`minjob-ingest status`의 몫). ⚠️ `_aborted`는 게시판이 아니라 실행이 끊긴 것이라 이름에서 빼고, **그 실행은 게시판 수치 대신 "실행이 중단됨"만** 말한다 — 크롤러는 예외를 잡고 실행을 닫으므로 `finished_at`이 채워지고 `sources_ok`가 손대지 않은 게시판까지 세서, 3번째에서 죽은 실행이 "전부 성공"으로 나가기 때문이다. 이름은 **이름순**으로 정렬한다(jsonb는 키를 길이순으로 저장해 그대로 쓰면 짧은 키만 늘 앞에 오고, 크롤러 화면과 같은 실행을 다른 이름으로 부르게 된다). ⛔ **경보를 여기서 판정하지 않는다** — 죽었나(3시간)·연속 실패(2회)·빈 목록(2회) 판정은 크롤러 `pipeline/health.py::alerts_for`가 정본이고 `minjob-ingest status`가 보여준다. 우리가 임계값을 한 벌 더 쓰면 언젠가 갈린다(`isPubliclyOpen` 사본을 만들지 않는 것과 같은 이유). 화면은 **저장된 사실만** 그리고 카드 아래에서 그 명령을 가리킨다. `finished_at`이 비면 **"끝나지 않음"이 아니라 "종료 기록 없음"**이고(지금 돌고 있는 중일 수 있다) 그때는 게시판 수치도 쓰지 않는다 — 집계가 끝나지 않아 0/0으로 남아 "게시판 0곳 모두 정상"이라는 거짓말이 된다(실측 08-24 17:01).
  - **공개** — 공개 중 · 내려감 · **공개 대기** + **공개 목록 새로고침**. 버튼이 화면 바닥의 각주가 아니라 이 카드 안에 있는 이유는 그 버튼이 다시 세게 만드는 것이 바로 위 세 숫자여서다(`updateTag("jobs")` → `getAdminOverview`). **공개 대기 = 승인했지만 아직 `jobs`에 안 올라간 건** — 승인이 조용히 증발하는 유일한 경로다(공개는 크롤러 다음 실행이 한다). **링크는 걸지 않는다** — 그것만 걸러 보는 화면이 없어서 필터 없는 목록으로 보내는 링크는 없는 것만 못하다. 색도 **그 칸에만** 준다(카드째 물들이면 옆의 공개 중·내려감까지 봐야 할 것처럼 보인다).

  **① 큐 — 조건은 이것뿐이다**

  ```sql

  ORDER BY created_at ASC          -- 오래 방치된 것 먼저
  ```

  ⚠️ **정렬 타이브레이크(`id`)는 `getQueueNavigation`과 짝이다**(2026-08-24). `created_at`이 같은 행이 생기면(크롤러가 한 트랜잭션으로 묶어 넣으면 Postgres `now()`가 고정돼 **전부 같아진다**) 목록과 앞뒤 이동의 정렬이 갈리고, 단건 화면의 "다음"이 목록의 다음 줄과 어긋난다. 묶음 화면의 줄 번호도 같은 이유로 `posted_on` 다음에 `id`로 못 박는다.

  ⚠️ `posted_at`은 **중복 묶음의 최신 게시일로 덮이는 파생값**이라 정렬 기준이 못 된다.

  **값은 읽기가 기본, 고치기는 펼쳐서**(2026-08-23) — 스무 칸을 전부 입력창으로 그려 놓으면 원문과 대조할 값이 컨트롤에 묶여 "결정할 게 너무 많은" 화면이 된다. 검수의 대부분은 **읽고 넘기는 일**이고 고치는 것은 몇 칸뿐이다.

  - ⚠️ **사례비 줄의 라벨은 값에 따라 바뀐다** — 사역직 `사례비` / 일반직 `급여`(`payLabel`이 정본 · DATA §3). 검수는 "공개되면 이렇게 보인다"를 확인하는 일이라 라벨도 공개 화면과 같아야 한다(2026-08-24 수정 — 큐에 일반직 5건이 `사례비`로 나가고 있었다). `ROW_LABELS`의 라벨 덮어쓰기는 **이 칸에만** 쓴다.

  - 포스터가 안 뜨면(signed URL 서명 실패 등) **원문 링크를 크게** 띄운다 — "그림 못 받음"(경로가 애초에 없음)과 다른 상황이다.
  - 원문 텍스트가 **빈 문자열인 것은 정상**이다(본문이 이미지 한 장인 게시판) — 포스터가 있으면 "원문이 그림입니다", 그것마저 없으면 **"대조할 원문이 화면에 없습니다"**(승인하지 말라는 뜻)로 갈라 말한다.

  **첨부 레인**(2026-08-23) — 이름·개수를 보여주고 **원문 링크로 보낸다. 여기서 열지 않는다.**
  - 첨부 URL은 게시판 세션에 묶여 있어(그누보드 계열 4곳은 상세를 먼저 GET해야 파일이 온다 · 크롤러 SPEC §6) 우리 화면에서 링크를 걸면 `잘못된 접근입니다` HTML이 열린다.
  - **이름이 같은 것을 합쳐 "같은 이름 N줄"로** 보여준다 — 게시판이 같은 파일을 여러 줄로 낸다(실측: 지원서 하나가 9줄).
  - ⛔ **파일명으로 "공고문 / 지원 양식"을 가르지 않는다** — 크롤러 실측에서 289건 중 24건이 두 키워드에 **동시 매치**했다(`교역자 초빙 서류.hwp`). **확장자로 "구조화가 읽었을 수 있나"만** 가른다(이미지 = 읽음). 못 읽은 첨부가 있으면 "값의 근거가 이 문서 안에만 있을 수 있다"고 경고한다 — 본문이 "첨부파일을 참고 하시고 지원해 주세요," 한 줄인 공고가 실제로 있다(실측).

  **함께 고쳐야 하는 칸** — DB CHECK가 짝을 강제한다. 가능하면 저장 전에 화면이 막는다.

  | `denomination` | `denomination_source='operator'` | 화면엔 교단이 보이는데 **공개된 공고엔 비어 있다**(크롤러는 확정된 교단만 공개한다: `stated`·`registry`·`operator`만) |
  | `denomination` 지우기 | `denomination_source='unknown'` | CHECK 위반 |

  ⚠️ **`housing_provided`는 3-state**다 — `true`(제공)·`false`(명시적 없음)·**`NULL`(공고가 말하지 않음)**. `jobs`도 nullable이라 `NULL`이 그대로 공개된다. **체크박스로 만들면 `NULL`이 `false`로 뭉개진다.**
  ⚠️ `pay_period`를 정할 수 없으면 **금액도 비운다** — 연봉이 월급으로 공개되는 사고를 막는다(DATA §12).

  **고칠 수 있는 칸** — 교회명 · 제목 · 종류 · 직분/직무명 · 부서 · 지역(광역+시군구) · 교단(+근거 자동) · 고용형태 · 사택(3-state + 원문 표현) · 사례비(최소~최대 + 주기 + 비정형) · 마감일 · 연락처 4칸 · 설명(2026-08-22) **+ 자격 · 주소 · 목록 칸 다섯**(`requirements`·`preferred`·`required_docs`·`optional_docs`·`process_steps` — 2026-08-23). 승격 6칸을 다 덮고, 거기에 **검색 축이 되는 칸**(지역·고용형태·자격), **노출 여부를 바꾸는 칸**(마감일), **지도가 쓰는 칸**(주소)을 더한 것이다. 마감일·게시일로 계산한 "승인해도 목록에 안 뜬다"는 경고를 판정 버튼 위에 띄운다(`isPubliclyOpen` 재사용).
  - **`requirements`를 열어 둔 이유**: `qualification`이 다섯 값뿐이어서 `본 교단 신학대학원`·`총회 인준 신학교` 같은 조건을 담을 수 없고, 그것이 빠지면 **다른 교단 지원자가 헛지원한다**(크롤러 실측 — 172건 중 23건에서 사라졌다). 나머지 넷도 지원자가 그대로 따라야 하는 것이라 성질이 같다.
  - 목록 칸은 **줄 단위로** 고치고·지우고·더한다. ⚠️ 한 덩어리 textarea로 두면 줄바꿈이 원소 구분이 되어 **원문에 줄바꿈이 있던 항목이 조용히 둘로 갈린다.** 빈 줄은 저장 전에 걷어낸다(`[""]`가 남으면 공개 화면에 빈 항목이 그려진다).
  - **여전히 못 고치는 칸**: 근무일 · 모집 인원 · 시작 시기 · 복리후생. 표시용이라 틀려도 지원 결과가 안 바뀌고, 칸이 늘면 한 건에 드는 시간이 늘어 큐가 밀린다 — 잘못됐으면 사유를 적고 거절한다. 화면은 **읽기 전용으로 보여준다**(승인은 "이대로 나가도 되나"를 묻는 일이라 나갈 것을 다 봐야 답할 수 있다).

  **승인 게이트**

  | | 조건 |
  |---|---|
  | **막는다** | 승격 6칸(`church_name`·`title`·`job_kind`·(`position`\|`role`)·`description`·연락처 4칸 중 1개) 중 빈 칸 — 크롤러가 `jobs` INSERT를 시도하다 CHECK로 실패한다 |

  | **막지 않는다** | 교단 미확정 — 교단 칸만 비게 나가고 공개 자체는 된다(경고만) |

  **쓰기 계약 — `review_data`만 쓴다**

  ```
  승인    고친 칸 + review_status='APPROVED' · reject_reason=NULL · reviewed_by · reviewed_at
  거절    review_status='REJECTED' · reject_reason='OPERATOR'(항상) · review_note(필수)
          · reviewed_by · reviewed_at        ← 고친 값은 저장하지 않는다(망가진 건도 거절해야 한다)
  되돌리기 ... WHERE id=$1 AND published_job_id IS NULL   ← 이 조건이 안전장치
  ```

  ⛔ **"저장만"은 없다**(2026-08-23 · 운영자 판단). 판정하는 두 길이 이미 `reviewed_by`를 찍으므로 "사람이 손댔다"는 표시에 빠지는 구멍이 없고, **값을 저장하는 경로는 승인뿐**이다. 오히려 저장만이 있으면 **판정하지 않은 행에 도장이 찍혀** 크롤러의 재구조화가 그 행을 건너뛴다 — 반쯤 고친 AI 초안이 영구히 굳는다. → `reviewed_by`가 찍힌 `PENDING` 행은 이제 **되돌린 건**뿐이고, 큐가 그렇게 표시한다.

  ⚠️⚠️ **중복 거절에 `reject_reason='DUPLICATE'`를 쓰지 않는다.** 크롤러는 그 값을 **자기가 내린 판정**으로 취급해 매 실행 처음부터 다시 보므로 **다음 실행이 거절을 풀어 버린다**(중복 규칙이 실측으로 계속 바뀌어 잘못 거절한 행이 되살아나야 하기 때문). 사람의 결론은 `'OPERATOR'`로 쓴다 — `OPERATOR`·`HERESY`·`CLOSED`는 결론 난 것으로 보고 판정에서 제외한다.
  ⚠️ **`reviewed_by`는 판정할 때 채운다.** 이 칸이 "사람이 손댔다"는 정본 표시고, 비면 **다음 재구조화가 사람의 교정을 AI 초안으로 되돌린다**(크롤러가 "지금 못 막는 유일한 구멍"이라고 적었다).
  → 그래서 **"오늘 처리"는 `reviewed_by`만으로 세지 않는다**(되돌린 건이 섞인다) — `review_status <> 'PENDING'`을 함께 본다. 큐 목록은 반대로 그 칸을 읽어 **"되돌린 건"** 을 표시한다.
  → **되돌리기는 사람이 내린 판정만** 대상이다. 크롤러 자동 판정(`reviewed_by` 빈 행)은 되돌릴 것이 없고(다음 실행이 다시 판단한다), 그래서 크롤러의 `DUPLICATE` 거절을 사람이 푸는 경로는 **만들지 않았다** — 풀려면 `dedup_state`(크롤러 계산값)도 함께 지워야 하는데 그건 다음 실행에 덮인다.
  → ⚠️ **되돌리기는 `reviewed_by`·`reviewed_at`을 지우지 않는다**(2026-08-22 수정). 지우면 "사람이 손댔다"는 표시가 사라져 **다음 재구조화가 운영자의 교정을 AI 초안으로 덮어쓴다** — 되돌리기는 "판정을 취소한다"는 뜻이고 "손댄 적 없다"가 아니다. 되돌린 행은 큐에서 "되돌린 건"으로 보인다.
  → ⚠️ **0행 UPDATE를 성공으로 읽지 않는다.** PostgREST는 조건에 맞는 행이 없어도 에러를 주지 않으므로 `.select("id")`로 바뀐 행을 돌려받아 확인한다. 안 하면 `published_job_id IS NULL` 안전장치가 막은 것을 화면이 "되돌렸습니다"라고 **거짓 보고**한다.
  - **손대지 않는 것**: `jobs`(크롤러가 공개한다) · `source_data`(write-once 원문 증거) · `dedup_key`·`dedup_state`·`confidence`·`published_job_id`·`posted_at`(전부 크롤러의 계산값. `dedup_state`는 중복 거절 해제 때만 예외)
  - **UPDATE는 한 번에 원자적으로** 보낸다 — 나눠 보내면 중간 상태가 CHECK에 걸린다.
  - ⚠️ **보내는 칸은 실제로 바뀐 것만**(2026-08-22). 안 고친 칸까지 함께 쓰면 운영자가 화면을 연 뒤 크롤러가 재구조화한 값을 **손댄 적 없는 칸까지 덮어쓴다**. 게이트는 고친 뒤의 **전체 상태**로, UPDATE는 **바뀐 칸만**으로 — `changedEdits`(lib/review-edits)가 그 둘을 갈라 준다. 짝(`job_kind`↔`position`·`role`, `denomination`↔`denomination_source`)은 화면 컨트롤이 언제나 함께 움직이므로 한쪽만 빠지지 않고, 그래도 어긋나면 CHECK가 막는다.

  **③ 묶음 — 같은 `dedup_key`를 나란히**
  - 멤버마다 **검수 화면 ↗** 링크(판정 대상 제외) — 거절된 건·대기 건도 원문과 값을 열어 봐야 같은 자리인지 판단할 근거가 된다(2026-08-29 · 한때 공개된 건에만 "공고 보기"가 있었다). **중복 처리의 메모는 비워도 된다** — 비면 “묶음 판정 — 같은 자리”로 남긴다(화면 자체가 근거다 · 단건 거절은 여전히 사유 필수).
  - 제목은 **건수로** 묻는다("이 3건이 같은 자리인가?"). ⚠️ 자리 이름을 제목에 넣으면 직분이 `ETC`일 때 **"기타 — 같은 자리인가"** 가 되어 무슨 화면인지 알 수 없다(2026-08-23 수정). 자리·부서는 그 아래 설명 줄로 내린다.
  - 구성원 줄은 **제목이 첫 줄**이다. 접수 이메일을 앞세우면(이전 모양) 사람이 못 알아보는 문자열이 주인공이 되고 판단 재료가 안 보인다. `dedup_state`는 줄에 쓰지 않는다 — 전원이 `UNCERTAIN`이라 같은 말만 반복된다. 대신 **판정 대상 / 공개됨 / 거절됨 / 공개 대기 / 검수 대기**를 쓴다.
  - **갈리는 값을 건별로 적는다**(2026-08-23) — 칸 이름만 나열하면("다른 점 — 접수 이메일 · 사례비") 무엇이 어떻게 다른지 몰라 판단이 안 된다. `groupDifferences`가 `{label, values[]}`를 돌려주고 각 줄이 자기 값을 뽑아 라벨과 함께 보여준다. ⚠️ **제목은 비교 칸에 넣지 않는다** — 재게시는 제목을 조금씩 바꿔 올려 거의 항상 "다른 점"이 되고, 그러면 목록이 제목으로 찬다(제목은 첫 줄에 통째로 있다). ⚠️ 비교값은 **라벨로 바꿔서** 비교한다 — 이제 화면에 그대로 나가므로 `ASSOCIATE_PASTOR`가 보이면 안 된다.
  - ⛔ **묶음 키와 "묶인 이유" 상자는 두지 않는다**(2026-08-23). 갈리는 값이 아래에 건별로 다 나와 있어 같은 말을 두 번 하고, 키(`교회명:지역:직분:부서:R1`)는 읽을 사람이 없다.
  - ⚠️ **순서·표시 날짜는 `source_data.posted_on`이다 — `review_data.posted_at`이 아니다**(2026-08-22). 후자는 묶음의 최신 게시일로 **덮이는 파생값**이라 구성원끼리 같은 값이 되고, 그러면 "어느 것이 먼저 올라왔나"라는 이 화면의 핵심 근거가 사라진다. 같은 이유로 **큐 목록의 날짜 칸도 `posted_on`** 을 쓴다 — 파생 게시일은 단건의 "그대로 공개되는 값"에서 라벨과 함께 보여준다.
  - ⚠️ **묶음의 일부는 이미 공개돼 있다** — 크롤러가 대표는 내보내고 나머지만 검수로 돌린다. 구분은 `published_job_id IS NOT NULL`. **이미 공개된 구성원에는 쓰지 않는다.**
  - "크롤러가 고른 대표"는 표시할 수 없다 — 대표와 나머지에 똑같이 `UNCERTAIN`이 붙어 저장값으로는 구분이 안 된다. 대신 공개 여부와 `review_status`로 보여준다.
  - 두 버튼 모두 **검수 대상에만** 쓴다: **같은 자리** → `REJECTED`+`OPERATOR`+`review_note` / **다른 자리** → `APPROVED`
  - ⚠️ `dedup_state`는 `UNCERTAIN`으로 남는다 → 그 자리는 **끌어올림을 받지 못한다**(끌어올림은 `MASTER`만). 알고 넘어가는 제약.
  - `dedup_key`는 **편집 불가** — 크롤러가 매 실행 다시 계산해 덮는다(판정은 멱등이어야 한다).

  **⚠️ 승인해도 즉시 공개되지 않는다** — `review_status`만 바뀌고 **다음 크롤 실행이 `jobs`에 넣는다**(공개는 중복 판정이 끝난 뒤에만 안전하다). **UI에 그 사실을 적는다** — 안 적으면 검수자가 승인하고 목록을 확인하러 갔다가 "안 됐다"고 판단해 다시 누른다. 공개 전이면 되돌릴 수 있다.

  - **처리된 신청**은 판정 버튼 없이 결과만 보여준다. ⛔ **되돌리기를 만들지 않았다** — 반려는 증빙을 파기했으니 되돌려도 열 서류가 없고(재신청이 그 경로다), 승인 취소는 **그 교회가 이미 올린 공고를 함께 내리는 규칙**이 있어야 성립한다(공고의 공개 판정은 `jobs.status`·마감일이지 교회 검증 상태가 아니다). 담당자 실명·직분·이메일은 검수 확인 목적 admin 전용 노출(공개 X, 가드레일 #3). **담당자 개인 전화는 아예 수집하지 않는다**(2026-08-18 — 사칭자가 자기 번호를 적고 자기가 받으므로 검증이 성립하지 않는다). 대조는 교회 **사무용** 연락처로 한다.
- → **거대 통계 대시보드·별도 교회관리 시스템은 안 만든다** (교회 생성·편집은 ingest/jobs 안에서 인라인).

## 수익화 — 광고·노출 (첫 매출 채널)

등록은 무료, **노출이 유료**. 교회가 결제하면 공고를 "더 많이·더 크게·눈에 띄는 위치"에 보여준다.

**자리는 셋, 상품은 사다리 3등급**(확정 2026-09-02 · ✅ 자리·라벨·상품표·요금 페이지 구현 2026-09-03 — 결제 적용·정원 판정은 결제 마무리 ROADMAP 1-8):

| 등급 | 걸리는 자리 | 동시 정원 | 1주 | 2주 | 4주 |
|---|---|---|---|---|---|
| **스페셜** | 홈 카드 + 목록 상단 + 연관 상단 3칸 | **3** | 69,000 | 129,000 | 209,000 |
| **플러스** | 목록 상단 + 연관 상단 3칸 | **2** | 49,000 | 94,000 | 149,000 |
| **기본** | 연관 상단 3칸 | 없음 | 29,000 | 55,000 | 89,000 |

- **자리별 규칙** — 광고는 **그 화면의 결과에 원래 들어갈 수 있는 공고일 때만** 맨 위에 선다.
  - **홈**: 히어로 아래 카드 **3장 고정**(PC 한 줄 · 모바일 세로). 항상. 안 팔린 칸은 최신 공고가 서고 라벨을 뗀다
  - **목록**: 1페이지 맨 위 로우 **최대 5줄**(스페셜 3 → 플러스 2 → 일반 최신순). **사용자가 건 필터를 통과한 광고만** 남는다. 정렬 1차 키가 아니다
  - **연관**(상세 하단 비슷한 공고 6장 중 **위 3칸** · 개정 2026-09-05, 그전엔 첫 칸 하나): 그 페이지의 **자격 문 통과 + 같은 지역**일 때. 광고가 3곳 미만이면 남는 칸은 유기 공고가 채운다. 넷 이상 겹치면 **페이지마다 3곳씩 돌아가며** 보인다(당번표 — 시작점만 기준 공고 id로 정하고 연달아 셋). 등급은 여기서 순서를 만들지 않는다(스페셜·기본이 같은 한 표). 비슷한 공고 규칙은 공고 상세 절
- **라벨**은 광고가 선 **카드·로우마다** 회색 텍스트 "광고" 한 단어(개정 2026-09-03 — 섹션 제목 옆 하나로 두면 안 팔린 칸의 최신 공고까지 광고로 읽히고, 필터로 광고 로우가 줄면 경계가 사라진다). 등급명·배경색·강조 없음(표시광고·신뢰). 라벨은 공고가 아니라 **자리**의 속성이다(`PlacedJob.ad` · 그리는 쪽이 넘긴다) — 같은 공고가 유기적으로 뜬 자리에는 붙지 않는다
- **시작일을 오늘부터 7일 안에서 고르고 그날부터 주수 × 7일** · VAT 포함 · 2주 −5% · 4주 −25%. **런칭 프로모션 없음**(운영자 결정) — 정가로 시작. 정원은 **동시 건수**라 어느 날이든 스페셜 3 · 플러스 2를 넘지 않는다(개정 2026-09-03 — 월~일 고정이면 목요일에 사도 1주 값이었다)
- 매진이면 자리가 나는 날부터 예약. **수요가 넘치면 정원이 아니라 값을 올린다** — 정원을 늘리면 먼저 산 교회 것이 묽어진다
- **노출 상태는 원장이 정본**이다(DATA §7 · 2026-09-03) — 오늘을 덮는 PAID 행이 그 공고의 등급이고, 기간이 지나면 조회에서 빠진다(별도 강등 배치 없음). 결제 완료 즉시 반영되며 운영자 몫은 환불(PortOne 콘솔 + 원장 상태)만

> **왜 이 모양인가(2026-09-02 재조사)** — 업계는 전부 "싼 단품 + 위에 묶음"이다(갓피플 스페셜=홈+목록 / 메디게이트 플래티넘 / 사람인·잡코리아 메인에 지면·헤드라인 번들). 값은 자리가 아니라 **닿는 범위**로 갈린다. 비율은 갓피플 4:2:1을 참고했다. ⚠️ **최상단은 9.9만 → 6.9만으로 내렸다**(운영자 결정 2026-09-05) — 갓피플 스페셜(8.8만/7일)에 값을 맞추던 근거를 버린 것이다: 우리는 트래픽 실적이 아직 없어 같은 급의 값을 부를 처지가 아니고, 첫 판매를 막는 것이 값 자체다. 그래서 비율도 2.4:1.7:1로 좁아졌다 — 사다리 간격이 준 만큼 상위 등급의 설득은 **자리 수**(홈 3칸·목록 5줄)가 해야 한다. 단품을 **연관**으로 잡은 이유: 우리 유입이 SEO라 상세 페이지가 트래픽이 닿는 자리이고, 지역별로 자연히 나뉘어 정원 계산이 안 얽힌다. 성과형(클릭·지원당)은 측정 인프라 0·트래픽 0이라 이번 라운드가 아니다. 끌어올리기·강조 add-on은 계속 제외. *사용자 노출 라벨 = **"공고 노출 안내"**.* 배너 광고(기독 B2B)는 Phase 2+ 옵션. **조사 근거·자리 목업·연관 규칙 = SNAPSHOT §9.**

> **미상(null)은 어느 칩에도 세지 않는다 = 칩 수의 합이 "총 N건"보다 작다.** 그게 이 숫자가 하는 말이다 — 부서 없는 공고 643/953건(실측 2026-09-04)은 부서를 고르는 순간 빠지고, 사용자는 그걸 **누르기 전에** 안다. ⛔ **"정보 없음" 칩도, 결과 위 안내 배너도 두지 않는다**(2026-09-04 검토): 부서가 빈 643건은 대부분 "모르는 것"이 아니라 **부서 개념이 없는 자리**(부목사·담임·사무간사 약 495건)이고, "정보 없음"으로 부르면 그게 거짓이 되며 유초등부를 찾는 사람에게 보여 줄 이유도 없다. 매 필터마다 뜨는 배너는 결함 공지로 읽힌다. **남은 진짜 결손은 데이터에서 고친다** — 제목에 부서·고용형태가 적혀 있는데 비어 있는 건(부서 68 · 고용형태 154)은 크롤러가 제목을 함께 읽어야 한다(min_job_agent 전달 사항).
> **차별 금지**: 성별·결혼여부는 채용차별 소지 → 필드·필터로 두지 않는다.
> **페이지당**: 20·50·100 (기본 20).

## 우선순위 (개요 — 작업 단위는 ROADMAP.md)

- **Phase 1 (MVP)**: 공개 열람(홈·목록·상세·교회) + 검색·필터, 로그인(단일 계정)·마이페이지·**북마크**, 교회 인증·공고 등록·수정, admin(ingest+jobs+인증 승인), 소개·약관·개인정보·문의
- **Phase 2 (차별화)**: 재공고 추적(**보류 해제 시**), 거리 기반 필터(지도 임베드), 광고·노출(3등급 실적용), 관심 교회 팔로우·새 공고 알림, 사후 신고
- **Phase 3 (고도화)**: 인재 DB, 사이트 내 지원 중개, 결제 연동(자동 과금), 공고 재등록 편의, 관심 조건 알림, 검색광고

- **잘림 방지**: `my-auto` 중앙(여유 시) + 넘치면 자연 스크롤. `?next=`·`?error=` 의존이라 폼은 `<Suspense>` 안 — 모드 `◐`(셸만 prerender).

### 마이페이지 `/mypage` + 교회 인증 `/mypage/verify` — 확정 2026-07-12 · 구현(mock) 2026-07-13
**모드**: dynamic + 인증. 게이트는 **2단**(2026-07-29) — ① `proxy.ts`가 렌더 전에 비로그인을 **진짜 307**로 돌리고(`/mypage/**`·`/jobs/new`·`/jobs/[id]/edit`·`/admin/**`) ② 각 페이지가 `<Suspense>` 안에서 `requireUser()`(`lib/auth-guard.ts`, 인자 없음)로 **최종 판단**한다. 복귀 경로는 proxy가 `x-pathname` 헤더로 넘겨주므로 **경로 문자열은 `proxy.ts` 한 곳**에만 있고 쿼리스트링도 보존된다. 2단인 이유: cacheComponents에선 uncached read(쿠키)가 `<Suspense>` 안이어야 해서, 페이지 안 redirect는 307이 아니라 **스트림 데이터(HTTP 200 + 스켈레톤)**로 나간다 — 그래서 proxy가 1차, 페이지가 최종이다(proxy 목록에서 빠져도 데이터는 새지 않는다). `(authed)` 그룹은 layout에서 `robots: { index: false }`를 상속시켜 게이트 이전 껍데기가 색인되지 않게 한다. 단일 계정 위에서 계정 상태로 분기. 권한 파생 = `hasChurchAccess(user)`(`lib/auth.ts` — `church_id` 연결 + status=APPROVED). Phase 1 = **사역자 view(최근 본·북마크) + 교회 view(`/mypage/church`) + 인증 흐름(`/mypage/verify`)**, 관심 교회·알림은 Phase 2.

> ⚠️ **교회 페이지는 현재 실질적으로 닫혀 있다(2026-07-29)**: `getCurrentUser`가 `churchId`·`churchName`·`churchVerificationStatus`를 **항상 null**로 준다(교회 테이블 미도입) → `hasChurchAccess`가 어떤 실 계정에서도 false. 따라서 `/mypage/church`·`/mypage/church/info`·`/mypage/church/promote`·`/jobs/new`·`/jobs/[id]/edit`·(당시의) `POST /api/payments/complete`에 아무도 도달하지 못한다. 아래 명세는 **교회 멤버십 배선 후 유효**하며, 상태 미리보기용 `?preview=none|pending|rejected` 어포던스는 제거됐다(ROADMAP Phase 1 ②트랙).

#### 교회 인증 신청 `/mypage/verify` — 실 배선 2026-08-25

**고유번호증 또는 사업자등록증이 있는 교회만** 신청할 수 있다. 인증은 "노출 자격"이 아니라 **"직접 등록·수정 자격"**이라, 서류가 없는 교회의 공고도 크롤 경로로 계속 공개된다(`church_id=NULL` · 카드·목록·필터가 쓰는 값은 전부 `jobs`에서 온다). 못 하는 것은 셀프서비스뿐이므로 **커버리지 손실 없이 정확도만 올라간다.** ⛔ 그래서 "서류가 없는 교회는 운영자에게 공고 등록 요청" 샛길을 없앴다 — 그 원칙을 우회하는 경로였다.

**흐름은 확인이 먼저다.**

1. **교회 확인** — 고유번호(숫자 10자리) 입력 → `lookupChurch`. 결과가 나오기 전에는 **2·3·4단계가 잠기고 제출 버튼도 잠긴다**(무엇을 저장할지가 정해지지 않았다).
   - **처음 등록** → 교회명·교단·지역·시·군·구·**상세 주소**(선택) 칸이 펼쳐진다
   - **이미 등록됨** → **교회명만** 보여주고 교회 정보 칸은 아예 없다
   - ⛔ **검색창(교회명으로 찾기)을 두지 않는다** — 이름으로 묶는 길은 실측으로 막혔다(2026-08-06: 검증 불가 67개 · 같은 연락처 다른 교회명 83건). 번호를 모르는 사람은 증빙 서류도 못 내므로 검색이 필요한 상황이 성립하지 않고, 검색은 표기 흔들림으로 **중복 교회를 만드는** 경로다
   - ⛔ **검증 상태(미검증/인증 완료)는 응답에 싣지 않는다** — "등록되어 있다"까지다. 그 이상은 운영자 판단이고, 알려주면 아무나 조회할 수 있다
   - 명시 버튼인 이유: 10자리를 채우면 자동 조회하는 방식은 오타로 10자리가 됐을 때 "처음 등록"으로 판정돼 칸이 펼쳐지고 고치면 다시 접혀 **깜빡인다**. 번호를 고치면 확인이 초기화된다
2. **교회 증빙** — 파일(**PDF·JPG·PNG·WEBP**, **4MB**) + 사무용 전화(필수)·이메일(선택)
   - ⛔ **HEIC·HEIF를 받지 않는다**(2026-08-26) — Chrome·Firefox가 렌더링하지 못해 **검수 화면에 띄울 수 없다.** 받는 형식은 "운영자가 읽을 수 있는 형식"이어야 한다: 못 띄우면 신청자는 올렸는데 판정이 막히고 결국 반려 → 재신청 한 바퀴다. 아이폰은 대체로 영향이 없다(iOS가 업로드에서 JPEG로 바꿔 보낸다). 화면에 적는 형식 목록도 **MIME 목록에서 파생**한다(`DOC_FORMATS_LABEL`) — 손으로 적어서 HEIC가 남아 있었다
   - ⚠️ **버킷 상한(10MB)이 아니라 4MB다** — 파일이 Server Action 본문으로 오고 **Vercel Function 본문 한도가 4.5MB**여서 그쪽이 실효 상한이다(DATA §7). 고르는 순간 크기를 재서 알리고 제출을 잠근다 — 서버까지 보내고 거부하면 헛업로드이거나, 4.5MB를 넘으면 액션에 닿기도 전에 플랫폼 `413`이라 에러 바운더리로 떨어진다
3. **담당자** — 이름·직분(필수) + 로그인 이메일(고정 표시)
4. **동의** — 필수. **방침 시행일이 화면에 찍힌다**(`PRIVACY_EFFECTIVE_DATE`) — 그 값이 `verification_consent_version`에 저장되므로 무엇에 동의하는지가 보여야 기록이 뜻을 갖는다. ⚠️ **약관과 방침의 시행일은 별 상수다**(2026-08-25 분리) — 하나로 묶으면 방침만 개정했을 때 **바뀌지 않은 약관까지 새로 시행된 것처럼** 보인다. 동의 기록에 쓰는 것은 **방침** 쪽이다

**저장 위치가 갈린다.** 교회 정보 6칸(`registration_no`·`name`·`denomination`·`region`·`city`·`address`)은 `churches`에, 나머지는 `users.verification_*`에.
- ⚠️ **기존 교회면 교회 칸을 저장하지 않는다**(보여주지도 않는다) — 미승인 신청자가 인증된 교회의 값을 덮어쓸 수 없다(DATA §3)
- ⚠️ **사무용 연락처는 `churches.contact_*`로 바로 가지 않는다** — 같은 이유다. **승인할 때 운영자가 옮긴다**
- ⚠️ **동의와 접수를 한 UPDATE로 쓴다** — `users_submitted_needs_consent` CHECK가 동의 없는 신청을 거부한다
- 교단 선택지에 **"무소속·독립교회"**(→ `null`)가 있다. `기타`("소속은 있고 우리 9키에 없는 교단")와 뜻이 다르고, 섞으면 필터·거점 판정이 오염된다. 신청서가 필수로 받으므로 **`churches.denomination`의 `null`은 늘 "무소속" 하나**다(`jobs`의 `null`은 "원문에 없음 = 미상")
- **상세 주소는 선택**이다(`region`·`city` 다음 조각만 받는다 — `서울 강남구`를 다시 적지 않는다). 오타가 나면 지도가 엉뚱한 곳을 짚으므로 승인 전에 증빙 서류와 대조한다. 주소 검색 도구(카카오)는 나중에 교회 정보 관리에 붙인다
- **시·군·구는 기초자치단체 하나**를 받는다 — `강남구`(자치구)·`용인시`(시)가 같은 레벨이고, `수지구`는 용인시 안의 **일반구**(자치단체 아님)라 한 단계 아래다. 그래서 `용인시 수지구`처럼 두 단어를 받지 않고 구는 **상세 주소**로 간다(`수지구 동천동 950-6`). 안내는 규칙 설명 없이 **예시 셋**만 준다(`CITY_HINT` · 폼 3곳 공용) — 규칙을 말로 적으면 읽고도 한 번 더 생각하게 된다(실사용 2026-08-26)
- ⛔ **시·군·구 select는 아직 만들지 않았다.** 법정동코드 정본으로 목록(기초자치단체 229개)을 만들 수는 있지만, 지금 이 폼을 쓰는 교회가 0곳인데 행정구역은 자주 바뀐다(2026년에만 인천 개편·화성 일반구·전남광주 통합 3건). 목록이 낡으면 그 지역 교회는 **자기 위치를 못 고른다** — 자유입력보다 나쁘다. 넣을 시점은 **지역 랜딩 라우트**(SEO)를 만들 때다: 그때는 닫힌 키가 URL에 박혀야 해서 목록이 필수고, 크롤 데이터 정규화도 함께 해야 한다. 재생성 절차는 ROADMAP

**상태 세 갈래** — `PENDING`=검토 중 안내(폼 없음) · `REJECTED`=**사유 + 폼**(사유 없이 빈 폼을 주면 무엇을 고칠지 모른다) · 그 외(`null`)=폼. 액션도 같은 판정을 해서 직접 POST를 보내도 거부한다.

**재신청은 같은 행을 덮어쓴다**(이력 테이블이 없다 · DATA §3). 그때 **옛 증빙 서류를 지운다** — 안 지우면 파기 경로 없는 개인정보가 쌓여 방침(`/privacy` §3)과 어긋난다. 순서는 `새 파일 업로드 → DB 기록 → 옛 파일 삭제`다(먼저 지우면 DB가 없는 파일을 가리킨다).

⚠️ **폼은 `<form action={액션}>`을 쓰지 않는다** — React는 폼 액션을 실행하기 **전에** `requestFormReset`을 무조건 부르므로(react-dom `startHostTransition` · 19.2 소스 확인), 칸별 오류를 돌려주면 **입력이 통째로 비워진 채 오류만 남고 고른 파일까지 사라진다**. `onSubmit`에서 `FormData`를 만들어 액션을 부르고 결과를 state로 받는다(브라우저에서 재현·확인 2026-08-25).
  - ⛔ **그래서 이 폼은 JS 없이 제출되지 않는다** — 로그인 폼과 다른 선택이다. 어차피 2·3·4단계 게이트가 **확인 결과(클라이언트 상태)**에 걸려 있어 JS 없이는 폼이 열리지도 않는다.
  - select 3개는 **"선택하세요"가 기본값**이다: 첫 옵션이 자동 선택되면 안 건드린 사람의 교회가 전부 `예장합동`·`서울`·`담임목사`로 저장된다.

⛔ **만들지 않은 것** — 결과 알림 메일 · 주소 검색(카카오) · 탈퇴 시 서류 파기(탈퇴 기능 자체가 없다) · 신청 이력 테이블 · 승인 취소. (승인·반려와 `churches.contact_*` 이관은 2026-08-26에 배선했다 — `/admin/verify/[id]` 절)

### 공고 등록·수정 `/jobs/new` · `/jobs/[id]/edit` — ✅ 실 배선 2026-08-27
**모드**: dynamic + 인증. **교회 인증 관리자만** — 비로그인은 `proxy.ts` 307 + 페이지 `requireUser`, 로그인했어도 `hasChurchAccess` 아니면 `/mypage/verify`로. 등록 **무료**이고 **검수가 없다**(인증이 게이트 · 가드레일 #1 개정 2026-08-21) — 등록하면 바로 `OPEN`이다. 신규·수정은 **같은 폼**(`JobForm`, `mode`로 초기값·카피만 다름). 폼 필드는 일반 채용 플랫폼 + 교단 게시판 실공고 조사 기반.
**쓰는 표는 `jobs` 하나다.** 교회 값(`church_name`·`denomination`·`region`·`city`·`address`)은 인증된 `churches` 행에서 **읽어 복사**하고 `churches`를 고치지 않는다 — 미검증 값이 인증된 교회를 덮으면 안 된다(교회 정보는 `/mypage/church/info`에서 고친다). `church_id`는 **세션에서** 오고 클라이언트에게 받지 않는다.
**형식**: **3스텝 위저드**(`max-w-3xl`). 상단 진행바(큰 단계) + 스텝 안 **왼쪽 섹션 타임라인**(점 구분 + 선 연결 + 스크롤 스파이로 현재 섹션 강조, `job-wizard.tsx`). **필수는 7개** — 제목·모집 종류·(직분 또는 직무명)·고용형태·본문 · **사택 제공** · 접수 방법. 별표(*) 표시 + "＊만 필수" 안내, Step 2엔 부담 완화 배너("사택 하나만 필수예요" · 공급 확보).
⚠️ **`employment_type`·`housing_provided`는 DB가 NULL을 허용하는데 폼에서는 필수다.** 근거는 같다 — 교회는 답을 알고 구직자에겐 결정적이다. 사택은 **있으면 자랑하고 없으면 침묵**하는 값이라 크롤 877건 중 "미제공"이 7건뿐이고(명시율 40% · 전임 71% · 파트 6%), 그 침묵을 그대로 물려받으면 구직자가 매번 교회에 물어야 한다 — 원문이 하지 않는 말을 받아내는 것이 "구조화"다. **`협의` 칩이 탈출구라 모르는 교회에게 거짓을 강요하지 않는다**(사례비를 필수로 하지 않는 것과 갈리는 지점 — 그쪽은 "내규"라 답 자체가 없을 수 있다).
- **Step 1 · 모집 기본**: ① 교회 정보(인증 교회 요약 — **읽기 전용**) ② 모집 내용(제목\*·**모집 종류\***·직분\* 또는 직무명\*·담당 부서·고용형태\*·모집 인원·부임 시기·근무 요일) ③ 자격 요건(**자격 enum 칩** + 프리셋 체크 + 직접 추가) ④ 우대 사항(프리셋 + 직접 추가) ⑤ **공고 본문\***(`description` — `NOT NULL`이라 필수다)
- **Step 2 · 처우·서류**(사택만 필수): ⑥ 사례비·예우(금액 또는 협의/내규 + **사택 제공\*** 칩 + 사택 설명 + 처우 비고) ⑦ **제출 서류**(프리셋 체크 + **항목별 필수/선택**, 담임용 목회계획서·설교영상·추천서 포함) ⑧ 전형 절차(자유 리스트)
- **Step 3 · 지원·마감**: ⑨ 지원 방법(링크·이메일·우편·전화 다중 + 접수처 — `contact_*` 4컬럼과 1:1) ⑩ 마감(마감일 또는 청빙 시까지=상시) ⑪ **미리보기**(접었다 펴는 자리)
**미리보기**: 마지막 스텝에서만(접었다 펴는 자리 — 별 스텝이 아니다). **공개 화면 컴포넌트를 그대로** 그린다(`JobCard`·`JobDetailView`) — 닮은 화면을 새로 만들면 공개 화면이 바뀔 때 조용히 거짓말을 한다. 탭은 **목록/상세 둘**이고 폭은 **모바일(390) 하나**다. **`<iframe>` 안에서** 그린다: Tailwind 반응형은 뷰포트를 보므로 `div`에 폭만 주면 데스크톱 레이아웃이 찌그러진 채 나온다. 값도 `toUpdate`를 통과시켜 **저장될 모양**으로 보여준다(숫자를 적으면 "협의" 표현이 버려지는 것까지 보인다).
⛔ **PC 폭 미리보기는 없앴다**(2026-08-27). 폼이 `max-w-3xl`(768px)이고 카드·구획 여백이 겹쳐 실제 자리는 **650px**인데, 거기에 1280px를 그리면 **0.51배로 줄어 글자가 읽히지 않았고**, 뭉개진 화면을 보고 "괜찮네" 하고 넘어가게 만들었다(거짓 안심). 미리보기의 목적은 **"내가 적은 게 어떻게 나오나"**(오타·빠진 값·사례비 표기)이지 반응형 검증이 아니고, 구직 교역자는 폰으로 본다(모바일 퍼스트). 목록 카드는 PC·모바일이 거의 같아 애초에 두 폭을 보여줄 값어치가 적었다. PC 폭을 제대로 보여주려면 미리보기가 **폼 밖으로 나가 화면 폭을 다 써야** 한다(모달 등) — 그때 이 결정을 뒤집는다.
**모집 종류는 하나만 고른다**(2026-08-26). `job_kind`는 배열이라 둘 다 담을 수 있지만 그건 크롤러가 원문 하나에 두 자리가 섞였을 때 쓰는 것이다(실측 863건 중 10건 = 1.2%). 교회가 올릴 때는 고용형태·사례비·부서가 **단일 값**이라 섞으면 한쪽이 거짓이 되고, 필터에도 어느 쪽으로 걸릴지 모호해진다. 등록이 무료라 두 번 올려도 비용이 없다.
**제외**(가드레일·차별화): **성별·연령·결혼 필드 없음**(관행이나 차별 소지) · 사이트 내 지원/이력서 시스템 없음 · 담당자 개인 휴대폰 강제 없음.
**⛔ 없앤 것**(2026-08-26 — 전부 *받아 놓고 버리던* 값이다): 직분·부서의 **"기타 → 직접입력"**(`position`·`department`가 닫힌 enum이라 자유 텍스트를 담을 컬럼이 없었다) · Step 3의 **"문의처"**(`jobs`에 컬럼이 없고 `contact_tel`이 이미 그 역할) · 교회 정보 **직접 입력 분기**(인증 교회는 항상 값이 있어 도달 불가) · **"정보 수정 문의" 메일 링크**.
**컬럼 커버리지**: `jobs` 41칸 중 **36칸을 등록이 채운다.** 안 채우는 5칸은 전부 의도된 자리다 — `id`·`created_at`·`updated_at`(DB), `status`(등록은 항상 `OPEN`, 마감은 상태 관리), `source_url`(교회가 직접 쓴 공고엔 원문 링크가 없다 — CHECK도 면제하고, 홈페이지는 `contact_link`가 받는다). 노출 칸 셋은 2026-09-03에 삭제됐다.
**사택은 칩 + 설명 두 칸**이다(2026-08-27). 칩만 있던 동안 폼이 저장된 `housing_note` 원문을 무조건 `"협의"`로 덮었다 — 크롤 863건 중 355건이 원문이고 69건엔 금액이 적혀 있다. ⚠️ `"협의"`는 교회가 쓴 글이 아니라 칩이 `provided=null`을 "정보 없음"과 가르려고 넣는 한 단어라, 되읽을 때 입력칸에 넣지 않는다.
**상태 관리**(`/jobs/[id]/edit` 하단): 모집 마감 ↔ 다시 모집. **삭제는 만들지 않는다** — 마감하면 이력이 남고 지우면 그 교회가 언제 무엇을 뽑았는지가 사라진다. "다시 모집"은 **기존 공고를 다시 여는 것**이고 복제가 아니다(복제하면 같은 자리가 목록에 두 번 뜬다).
