## 0. 전제

**홈 `/` = ✅ 완료(기준).** 딥그린 히어로(검색 오버레이+지표3) · 추천 청빙(`FeaturedJobCard`) · 2단(JobRow 리스트 + 사이드바) · 딥그린 헤더/푸터 bookend. 이 문서의 모든 제안은 홈에서 정립된 언어의 **조합**이며, 홈·헤더·푸터·`globals.css` 토큰·기존 컴포넌트는 재설계하지 않는다.

**재사용 인벤토리(이걸로만 조합)**
- 공고 표시: `JobRow`(텍스트 우선 리스트 행) · `JobCard`(그리드 카드) · `FeaturedJobCard`(대표광고 전용) · `BookmarkButton` · `RelativeTime`
- 탐색: `SearchBox`(홈 오버레이) · `JobFilter`(칩 그룹+사례비) · `Pagination` · `RecentlyViewed`
- 교회: `ChurchChannels` · 상세: `JobActions`(저장·공유)
- 셸: `Header` · `Footer` · `HomeSidebar` · `LegalDoc` · shadcn `Card/Badge/Button/Input/Sheet`
- 문법: 딥그린 `--primary` 토큰, 골드는 로고·히어로 eyebrow에만(콘텐츠 영역 골드 금지), 화이트 `bg-card` + 구분선 흐름(카드 파편화 금지), `break-keep`, 사례비는 값 있을 때만 초록, 광고는 배지·슬롯으로만 구분(틴트 없음)

# A. 공개 읽기

### 페이지: `/jobs` — 공고 검색·필터·비교의 메인 화면 (구직자 1순위 목적지)

- **모드**: 쿼리 없는 목록은 `'use cache'`, 검색·필터·정렬·페이지가 URL 파라미터로 붙으면 dynamic(`<Suspense>`). 현재는 mock 클라 필터(확정된 과도기 방식) — DB 전환 시 `filter-jobs.ts` 로직을 query 함수로 옮기고 URL(`?q=&region=&page=`)을 단일 소스로 승격. **필터 상태 ↔ URL 동기화**는 지금 클라 단계에서도 해두면 전환 비용이 준다(공유·뒤로가기·SEO에도 이득).
- **섹션(순서대로)** — 2026-07-01 확정 구조 유지, 재설계 없음:
  1. **페이지 헤더** — "사역자 청빙" + 한 줄 설명. 트래픽이 검색엔진→이 페이지로 직행하므로 맥락 제공.
  2. **검색바 + (모바일) 필터 트리거** — 결과 내 라이브 필터. 홈과 달리 오버레이 없음(확정).
  3. **추천 청빙(대표광고)** — `FeaturedJobCard` 2열, 필터와 무관하게 항상 노출(광고 계약 가치).
  4. **좌 필터 사이드바** — `JobFilter`(교단·지역·직분·부서·고용형태 칩 + 사례비 range + 협의 포함).
  5. **목록 헤더** — 총 N건 + 정렬. ❓ 정렬 축은 재검토 중(아래).
  6. **공고 리스트** — `JobRow`, 프리미엄 상단 고정.
  7. **우측 레일**(lg↑) — `RecentlyViewed` + 배너 슬롯(점선 placeholder 유지).
  8. **페이지네이션** — 8건/페이지.
- **레이아웃/디자인**: 현재 구현이 확정 톤과 정합. 소폭 다듬기만 제안 —
  - 필터 사이드바 카드를 홈 사이드바와 같은 문법(`rounded-xl border bg-card p-4 shadow-sm`)으로 통일(현재 `rounded-lg border`만). 시각 위계 변화 없음.
  - **활성 필터 요약 칩**: 필터 적용 시 목록 헤더 아래에 선택값 칩(`bg-primary/[0.06] border-primary/20` — 추천 검색어 칩과 동일 문법) + 개별 X. 모바일에서 Sheet를 닫으면 무엇이 걸려 있는지 안 보이는 문제 해결. 신규 컴포넌트 1개(`ActiveFilterChips`)로 작게.
  - 모바일: 필터 트리거 버튼에 활성 개수 배지(`필터 2`) 표시.
- **mock 데이터**: `JobCard` projection으로 충분. 추가 필드 불필요. 단 **부서 재설계(세분화+복수선택+교단별 별칭, ROADMAP 1-7)가 미착수** — 확정되면 `department: Department[]`화 + 필터·검색어 완성의 동의어 처리가 이 페이지에 직격. 지금 디자인은 현행 enum 기준으로 두고 재설계를 막지 않는 구조(칩 그룹은 옵션 수 늘어도 "더보기"로 흡수됨).
- **빈 상태 / 로딩 / 엣지**: 결과 0건 = 현행 문구 유지 + **"필터 초기화" 버튼 추가**(지금은 사이드바까지 가야 초기화 가능). 로딩 = 목록 영역만 JobRow 스켈레톤 5~6행(레이아웃 시프트 방지). 대표광고 0건이면 섹션 자체 숨김(현행). `?q=`에 결과 없는 검색어가 와도 동일 빈 상태.
- **열린 질문**:
  - ❓ **정렬 축**: 사례비순("세상적", 인터뷰)·마감임박순(교회 마감 개념 모호) 재검토가 ROADMAP 1-2에 걸려 있음. 제안: **최신순 단일 + "마감 표기만"**(정렬 아님)으로 축소하는 안 vs 현행 3축 유지 — 사람 결정 필요.
  - ❓ 필터 상태 URL 동기화를 mock 단계에서 먼저 할지, DB 전환과 함께 할지.

### 페이지: `/jobs/[id]` — 공고 상세: 구조화 정보 + 교회 채널 + 지원 안내 (★다음 코드 작업)

- **모드**: on-demand `'use cache'`(목표) / 현재 PPR(`generateMetadata` + JobPosting JSON-LD + `<Suspense>`). 시간 표시(`RelativeTime`)·북마크는 클라이언트 — cached scope 안전.
- **섹션(순서대로)** — 확정 시안(핵심조건을 좌측 본문 상단으로) 구체화:
  1. **헤더**(본문 카드 내) — 교회 아바타·교회명(→교회상세)·교단·지역 · 등록일 · `JobActions`(저장·공유) / 재공고 배지 + 직전 마감일 / 제목 / 직분·부서·고용형태 한 줄. 현행 유지.
  2. ★ **핵심 조건**(신규 위치 — 제목 바로 아래) — 사례비·마감·출근·고용형태·제출서류. 인터뷰 근거: "오른쪽에 빼면 시선이 제일 마지막에 가는데 제일 중요한 부분".
  3. **자격 요건** / **우대 사항** — 체크 리스트(초록 체크). 현행 유지.
  4. **공고 안내** — 본문(운영자 요약 or 교회 작성).
  5. **교회 정보** — 교회 요약 + 상세 링크 + 이 교회의 다른 모집.
  6. **우측 sticky**(경량화) — **지원 안내 CTA**("원문 공고 보기" / "교회 홈페이지") + "직접 지원 안 받음" 안내 + ★**교회 채널**. 핵심 조건이 빠져 카드가 짧아지고 sticky 가치(스크롤 내내 CTA·채널 고정)가 오히려 커짐.
  7. **하단** — 비슷한 공고(`JobCard` 그리드) · 출처 표기 + 오류 문의.
- **레이아웃/디자인**(핵심 조건 블록 구체안):
  - 컨테이너: `rounded-xl border border-primary/15 bg-primary/[0.04] p-4 sm:p-5` — 홈 추천검색어 칩과 같은 "옅은 초록 면" 문법. 요란하지 않게 면 하나로만 구분.
  - 데스크톱: 좌측에 **월 사례비**(값 있으면 `text-xl font-bold text-primary`), 우측에 `dl` 2×2 그리드(마감일·출근·고용형태·제출서류, 라벨 `text-xs text-muted-foreground` / 값 `text-sm font-semibold`). 모바일: 사례비 상단 한 줄 → 아래 2열 그리드 스택.
  - **사례비 비공개 다수 대응**(인터뷰: "거의 내규에 따름"): 값이 없으면 초록·큰 글씨 강조를 **하지 않고** `stipendNote ?? "협의"`를 일반 굵기·`text-foreground`로. "협의"가 주인공처럼 보이는 어색함 방지. 전면 강조 지양 원칙과 일치.
  - 마감: `deadline ?? "상시모집"`. D-day 계산은 비결정적(현재 시각) → 표시하려면 클라이언트 컴포넌트로(RelativeTime 패턴). 기본은 날짜 그대로가 안전.
  - 모바일 순서: 헤더 → 핵심 조건 → **지원 CTA 인라인**(핵심 조건 박스 직후, `buttonVariants size:lg` 풀폭) → 본문 → 채널. 우측 사이드바 내용이 모바일에서 위로 오던 현행(`order-first`)은 폐기 — 핵심 조건이 본문에 있으니 중복.
- **mock 데이터**: 확정 필드로 충분(`workDays·requirements·preferred·requiredDocs·description·source·sourceUrl`). 추가 없음.
- **빈 상태 / 로딩 / 엣지**:
  - `getJobDetail` null → `notFound()`(현행). 로딩 = 현행 스켈레톤 유지(그리드 비율만 새 레이아웃에 맞춰 조정).
  - **CLOSED 공고**(신규 제안): 현재는 마감 공고도 그대로 렌더됨. 상단에 무채색 배너 "이 공고는 마감됐어요" + 비슷한 공고로 유도, 지원 CTA는 비활성 대신 **"원문 보기"만 유지**(사실 확인 용도). SEO상 마감 공고도 페이지는 살려두는 게 재공고 이력·롱테일에 유리.
  - `sourceUrl`도 홈페이지도 없는 교회 직접 등록 공고 → CTA 없이 안내 문구만(현행 로직이 이미 처리, 문구만 "교회에 직접 문의해 주세요"로).
- **열린 질문**:
  - ❓ **모바일 하단 고정 CTA 바**(스크롤 후 "원문 공고 보기" 재노출): 채용 사이트 표준 패턴이지만 "조용한 톤"과의 긴장. 기본안은 인라인 CTA만, 고정 바는 사람 결정.
  - ❓ CLOSED 공고의 JSON-LD: `validThrough` 지난 JobPosting을 유지할지 제거할지(구글 가이드라인은 마감 시 구조화 데이터 제거 권장 — SEO 확인 필요).

- **빈 상태 / 로딩 / 엣지**: 남의 공고 or 운영자 공고 접근 = 403 성격 → `notFound()` 처리(존재 노출 최소화) / 수정 저장 후 상세로 redirect + 캐시 무효화로 즉시 반영 / 마감 처리 후에도 edit 접근 가능(다시 모집 경로).
- **열린 질문**: ❓ "다시 모집"이 기존 공고 재오픈인지 새 공고 복제인지 — 재공고 추적(같은 자리 반복 집계)에 직접 영향. 새 공고 생성이 이력에 정직(추천)하지만 교회 편의는 재오픈이 나음. 사람 결정 필요(Phase 3 "재등록 편의"와 연결).

# C. admin — 운영자 1인의 "공고 입력 작업대". 거창한 시스템 X. 공개 셸과 분리된 최소 셸(현행 admin layout) 유지.

> 디자인 원칙: admin은 **본인만 쓰는 데스크 도구** — 브랜드 연출 불필요, 중립 무채색 + 기능 밀도 우선. 모바일 퍼스트 원칙의 의도적 예외(수집·구조화 작업은 데스크톱에서 함). 단 깨지지 않을 정도의 반응형은 유지.

### 페이지: `/admin/jobs` — 등록 공고 전체 관리 (수정·삭제·상태·노출)

- **모드**: dynamic + admin 인증(proxy). 캐시 안 함(항상 fresh — 관리 도구). mutation은 `actions.ts` + `updateTag("jobs")`·`updateTag("job-{id}")`.
- **섹션(순서대로)**:
  1. **툴바** — 상태 필터 탭(전체 · 모집중 · 검수중 · 마감) + 출처 필터(운영자/교회) + 텍스트 검색(제목·교회명) + "수집 등록 →"(→`/admin/ingest`) 버튼.
  2. **공고 테이블** — 행: 제목(→공개 상세 새 탭) / 교회명 / 직분·부서 / 출처(`JOB_SOURCES` 라벨) / 노출 등급 / 상태 / 게시일 / 액션(수정·마감·삭제). 데스크톱 테이블, 좁은 화면에선 행이 카드형으로 스택.
  3. **행 인라인 액션** — 상태 변경(모집중↔마감, 검수중→게재 승인)과 노출 등급 변경(일반↔프리미엄↔대표광고 — Phase 2 결제 수동 처리의 실행 도구)은 행에서 바로. 필드 수정은 별도 수정 화면(ingest 폼 재사용)으로.
- **레이아웃/디자인**: `max-w-5xl`(현행 admin 폭). 중립 `bg-card` 테이블 + 상태는 `Badge`(모집중=default, 검수중=outline, 마감=secondary), 노출 등급은 텍스트 라벨(광고를 요란하게 구분하지 않는 원칙은 admin에도 — 등급은 정보지 장식이 아님). 삭제는 confirm 필수. 페이지네이션은 공고 100개 넘어가면 추가(그전엔 전체 렌더로 충분 — YAGNI).
- **mock 데이터**: mock 안 만듦(실 DB 위에서). 필요 스키마 = 공개와 동일 + `PENDING` 상태, `featuredTier` 수동 변경 이력은 두지 않음(1인 운영 — 과함).
- **빈 상태 / 로딩 / 엣지**: 필터 결과 0건 = 한 줄 문구 / 검수중 탭에 신규 교회 첫 공고가 모임(ROADMAP 1-4 검수 동선의 실체가 이 탭) / 삭제는 소프트 삭제 ❓(재공고 이력 보전과 충돌 — 이력 근거인 공고를 하드 삭제하면 타임라인이 왜곡됨. 소프트 삭제 권장, DATA 결정 필요).
- **열린 질문**:
  - ❓ 소프트 삭제 vs 하드 삭제(위 — 재공고 추적 정합성).
  - ❓ 교회 정보 수정 진입점 — 별도 `/admin/churches`를 안 만들기로 한 스코프에서, 교회 필드 수정은 공고 수정 화면 안의 교회 섹션에서 겸하는 안(추천) vs 최소 교회 편집 화면 추가.

### 페이지: `/admin/ingest` — 수집 텍스트 붙여넣기 → AI 구조화 → 검토 → 등록 (운영자 핵심 작업 화면)

- **모드**: dynamic + admin 인증. AI 구조화 호출은 Server Action(`lib/ingest/*` — 입력은 **항상 사람이 붙여넣은 텍스트**, 외부 fetch 코드 금지 = 가드레일 #1). 등록 액션 끝에 `updateTag("jobs")`.
- **섹션(순서대로)**:
  1. **가드 안내 헤더** — "사람이 확보한 공고 텍스트만 붙여넣으세요. 공공·교단·신학교 공식 게시판 우선, 영리 청빙 사이트 출처 금지"(가드레일 #1·#4를 화면 카피로 상시 노출 — 미래의 나에게 거는 안전벨트).
  2. **좌: 원문 입력** — 큰 textarea(원문 텍스트) + **출처 URL 입력**(필수 권장 — `sourceUrl`이 "원문 보기" CTA의 근원) + "구조화" 버튼.
  3. **우: 구조화 결과 검토 폼** — AI가 채운 공고 필드 전체(제목·직분·부서·고용형태·사례비 min/max/note·출근·요건·우대·서류·본문 요약·마감). **교회 매칭 블록**: 기존 교회 검색 선택(교회명 자동 매칭 제안) vs 신규 교회 생성 서브폼(교단은 enum 드롭다운). AI가 **개인 담당자 연락처를 추출해도 저장 필드가 없어 자동 폐기**되게 설계(가드레일 #3) — 감지 시 "개인 연락처가 감지되어 제외했어요" 경고 표시.
  4. **등록** — "운영자 등록으로 게재"(`source=OPERATOR`, owner 없음 — 가드레일 #2) → 성공 시 폼 리셋 + 등록된 공고 링크 토스트. 연속 입력(하루 수십 건)을 전제로 리셋 동선을 빠르게.
- **레이아웃/디자인**: `md:grid-cols-2` 2단(현행 스캐폴드 방향 유지 — 좌 원문·우 폼을 나란히 두고 눈으로 대조하는 게 이 화면의 본질). 좁은 화면 스택. 폼 필드는 `/jobs/new` 폼 컴포넌트·칩 문법 재사용(공개 폼과 동일 어휘 = 유지보수 1벌). AI가 채운 값 중 **확신 낮은/비어 있는 필드는 배경 옅은 노랑이 아니라 `border-destructive/40` 아웃라인 + 라벨 옆 점 표시**(새 색 안 만들고 기존 destructive 토큰 활용)로 검토 유도.
- **mock 데이터**: mock 안 만듦. 필요한 것 — `lib/ingest/` 구조화 함수(텍스트→`Partial<Job> + churchGuess`), AI 응답 스키마(신뢰도 플래그 포함 ❓ 형태 미정), 프롬프트에 "개인 연락처 무시" 명시.
- **빈 상태 / 로딩 / 엣지**: 구조화 처리 중 = 우측 폼 영역 스켈레톤 + 버튼 disabled / AI 실패·저품질 = 빈 폼으로 수동 입력 fallback(도구가 없어도 등록은 가능해야 함) / 같은 출처 URL 재등록 시도 = 경고(중복 수집 방지 — 재공고와 구분: 같은 자리 새 공고는 정상, 같은 원문 재입력은 실수) / 교회 매칭 모호(동명 교회) = 지역으로 구분 제시.
- **열린 질문**:
  - ❓ AI 모델·비용 정책(구조화 1건당 비용 상한, 로컬 재시도 정책) — 아키텍처 결정 필요.
  - ❓ 중복 감지 기준: `sourceUrl` 정확 일치만 볼지, 교회+자리+기간 근접까지 볼지(후자는 재공고와의 경계가 애매해져 보수적으로 URL만 권장).
  - ❓ 원문 텍스트 원본을 DB에 보관할지(검증·재구조화엔 유리하나 "원문 통째 복제 금지" 원칙과 긴장 — 비공개 보관이면 허용 범위인지 법률 검토와 연결).
